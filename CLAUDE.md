0. КЛЮЧЕВОЙ АРХИТЕКТУРНЫЙ ПРИНЦИП (ЧИТАТЬ ПЕРВЫМ)

Это SaaS-платформа, а не просто CRM.

Tenant (Тенант) — это компания-клиент. У каждого тенанта своя физическая база данных (Database-per-Tenant, пакет stancl/tenancy).
Branch (Точка) — физический адрес/подразделение внутри тенанта, ГЛАВНАЯ операционная единица (см. п.4 — раньше называлась "Филиал", переименована, чтобы не путать с классическим "подразделение юрлица": здесь наоборот, юрлица подключаются к точке, а не точки к юрлицу). Один тенант может иметь много точек.
Core (Ядро) — общий код платформы. Любая кастомизация тенанта (кастомные поля, формы) живет рядом с ядром в БД тенанта, а не меняет таблицы ядра.
Изоляция: Любая сущность, запрос, кеш-ключ или очередь обязаны быть в контексте конкретного тенанта. Забытый tenant-scope = утечка данных между компаниями. Это критический баг.
1. WORKFLOW АГЕНТА И ИНСТРУМЕНТЫ (TOOLS)

Твоя автономная работа строго регламентирована. Для задач, изменяющих код, правильная последовательность действий:

Read — прочитай существующий файл, если собираешься его менять.
Edit/Write — вноси изменения напрямую в рабочую копию (working tree). Edit — точечная правка (diff), Write — только для новых файлов или полной перезаписи. Отдельного шага "сохранить черновик" и ожидания применения патча человеком не существует — изменения сразу оказываются в файловой системе проекта.
Bash — используй для проверки (php -l, npx vite build, php artisan test), для git-операций и для любых shell-команд.
Git commit — НИКОГДА не коммить самостоятельно, если человек явно не попросил ("закоммить изменения" и т.п.). Внесённые правки остаются в рабочей копии как незакоммиченные изменения до отдельного явного запроса.
Ветки — не создавай feature-ветки автоматически; работай в той ветке, что уже активна, если человек явно не попросил создать новую.
Pull Request — создавай (gh pr create) ТОЛЬКО по явной просьбе человека, и только после того, как изменения закоммичены.

4. БИЗНЕС-ЛОГИКА И СУЩНОСТИ
Точка (Branch) vs Юрлицо (Legal Entity) — многие-ко-многим (с 2027_01_28, переименовано из "Филиал"):
    * Точка — главная операционная единица, физический адрес/подразделение: Сотрудники, Расписание, Склады, Заказы, Клиенты — всё висит на ней. Обязательна всегда (branch_id — не изменилось). Одной точки достаточно для работы вообще без единого юрлица (документы просто будут без реквизитов, никакой ошибки).
    * Юрлицо — исключительно финансовый профиль (Кассы, Реквизиты, подписанты для документов). Юрлицо не бывает "само по себе" — обязательно привязано хотя бы к одной точке (кроме самой первой точки в системе, которая создаётся автоматически — см. ниже), но привязка настраивается СО СТОРОНЫ юрлица (Settings/LegalEntities — мультивыбор точек), не со стороны точки.
    * Связь `branch_legal_entity` (пивот, без дополнительных колонок) — заменила старую единственную колонку `branches.legal_entity_id` (1:0..1). Причина: одна точка нередко реально выставляет документы от нескольких юрлиц одновременно (например, часть заказов — от ИП, часть — от ООО), а старая схема такое не могла выразить без завода "точек-дублей". `Branch::legalEntities()` / `LegalEntity::branches()` — обе BelongsToMany.
    * Раз у точки может быть несколько юрлиц, "какое юрлицо у ЭТОГО конкретного заказа" больше не выводится однозначно через branch — у WorkOrder есть собственное nullable `legal_entity_id` (тот же паттерн стоит добавить для Client/Transaction при необходимости — на момент написания реализовано только для WorkOrder). `DocumentPlaceholderService::resolveLegalEntity()`: приоритет — явный `$entity->legal_entity_id`; иначе — юрлицо точки, ТОЛЬКО если оно у неё ровно одно (иначе неоднозначно); если и так не определить — null, документ формируется с пустыми реквизитами (`DocumentGenerationService` не бросает исключение — точка/заказ имеют право работать без юрлица). Нумерация документа без юрлица — не через DocumentNumerator (тот атомарно скопирован именно на legal_entity_id, NOT NULL FK), а через сентинел-схему `БН-<дата>-<рандом>` — такой документ не претендует на бухгалтерскую сплошную нумерацию.
    * WorkOrderController::store()/update() валидируют legal_entity_id серверно (не только фронтом): выбранное юрлицо обязано реально входить в branch->legalEntities() этой точки — иначе ValidationException.
    * Автобутстрап: LegalEntityController::store() при Branch::count() === 0 (не "это первое юрлицо", а именно "точек в системе вообще нет" — так срабатывает и для тенанта, который все точки удалил) сам создаёт точку «Основная» и сразу привязывает к ней новое юрлицо — без этого первое же создание заказа у только что зарегистрированного тенанта (RegisterTenantController точку не создаёт) упёрлось бы в пустой список точек.
    * Сайдбар (AppHeader.vue): переключатель юрлица (если их >1) и точки (если доступно точек >1 после фильтра по выбранному юрлицу, включая точки без единого юрлица) — независимые кнопки. LegalEntityController::switch() сбрасывает выбранную точку на "Все" ТОЛЬКО если она не входит в новое юрлицо (а не всегда, как было раньше) — точка с несколькими юрлицами не заставляет пользователя перевыбирать её при каждом переключении юрлица. BranchController::switch() автоследует в юрлицо точки, только если оно у неё РОВНО одно (иначе никакого умолчания, выбор явно за пользователем).
    * Формы, создающие записи под точкой (WorkOrders/Index.vue, WorkOrders/Show.vue) — поле «Юрлицо» показывается только если у выбранной точки есть хоть одно юрлицо; если в сайдбаре уже выбрано конкретное юрлицо — поле дефолтится на него и БЛОКИРУЕТСЯ (сменить можно только через сайдбар, чтобы не путаться, от чьего имени реально выставляются документы); если у точки ровно одно юрлицо — то же самое, автоматически.
    * BranchScope (глобальный scope у WorkOrder/Client/Transaction/... — критичный tenant-isolation код, "особая осторожность") при "точка = Все, юрлицо = конкретное" фильтрует через whereHas('legalEntities', ...), НЕ через колонку (её на branches больше нет) — это было живым багом в процессе миграции (SQL-ошибка "unknown column legal_entity_id" на любом списке при выбранном юрлице), исправлено, покрыто живым HTTP-тестом с двумя разными юрлицами.
Склад и Типы учета:
    * Режимы склада: per_branch (раздельный), shared (общий), mixed (смешанный). Резолвинг склада идет через WarehouseResolver.
    * Типы учета товаров: average (средневзвешенный для химии) и batch (партионный/FIFO для дорогих пленок).
Универсальные справочники (Lookups):
    * Простые списки (источники клиентов, типы кузова) хранятся в единой таблице lookups. На фронте используется компонент <CreatableSelect> для добавления на лету.
Финансы (Accounts / Transactions):
    * Счета (Account) бывают 4 типов: cash (касса), bank (расчетный счет), acquiring (эквайринг, имеет commission_percent), bonus (единственный системный виртуальный счет тенанта для оплаты бонусами клиента — не привязан к юрлицу, не редактируется через обычную форму счетов).
    * Любое изменение Account.balance — ТОЛЬКО через FinanceService (processTransaction/processTransfer/updateTransaction/revertTransaction). Никогда не трогай balance напрямую в контроллере.
    * У Transaction есть transaction_date (бизнес-дата операции, редактируется, можно вносить задним числом) отдельно от created_at (техническая метка создания записи, никогда не меняется).
    * Редактирование транзакции — O(1) пересчет баланса счета дельтой (новая сумма минус старая), а не полный пересчет по истории.
    * Сверка (is_reconciled) блокирует правку суммы/даты, пока не снята. Закрытие периода (finance_period_closures, PeriodClosureService::assertNotClosed) блокирует создание/правку/отмену операций с датой не позже границы закрытия — обе проверки живут внутри FinanceService, не дублируй их в контроллерах.
    * Дневные снэпшоты остатков (account_daily_snapshots, AccountSnapshotService) считаются независимо по каждой дате (не цепочкой от предыдущего дня).
    * Автоподстановка банка по БИК — App\Services\DadataService::lookupBank() (DaData Suggestions API, findById/bank), вызывается из AccountController::lookupBik() (GET /settings/accounts/bik-lookup). Токен — тот же паттерн, что wappi_master_token (Фаза 16): App\Models\Central\PlatformSetting (central БД, ключ dadata_api_key, вносится администратором платформы в /admin/settings), читается из тенантского кода ТОЛЬКО через tenancy()->central(...) — тенант сам ключ не вводит и не видит. Settings/LegalEntities/Index.vue держит bank_name/corr_account нередактируемыми (readonly), пока DaData настроена и БИК валиден — защита от рассинхрона названия банка и БИК в документах; ЕСЛИ ключ не настроен (DadataService::isConfigured()===false) — фолбэк на ручной ввод с явным предупреждением (не блокируй создание счетов из-за неподключённой сторонней интеграции). Банк с state.status!=='ACTIVE' (отозванная лицензия) DaData всё равно возвращает в suggestions — lookupBank() отфильтровывает такие результаты как null.
Коммуникации (Мессенджеры, Фаза 11, фундамент):
    * Провайдер-абстракция: остальной код НИКОГДА не обращается к Wappi.Pro/Green API/SMS Aero напрямую — только через App\Services\Messaging\MessengerProviderInterface (чат-провайдеры: sendText/sendMedia/getConnectionStatus/getQrCode/provisionProfile/releaseProfile/parseIncomingWebhook/syncStatusFromWebhook) и отдельный App\Services\Messaging\SmsProviderInterface (только sendSms — у SMS нет диалога/QR/входящих, не смешивай с чат-интерфейсом). Конкретный класс выбирается по Channel.provider через MessengerProviderFactory::make()/SmsProviderFactory::make() — переезд на другого провайдера мессенджеров ограничивается новой реализацией интерфейса плюс веткой в фабрике, больше нигде в системе провайдер не упоминается явно.
    * Channel — одно подключение (один номер/бот/SMS-аккаунт); можно завести сколько угодно штук (например, по номеру на точку) — Channel.branch_id nullable (null = общий на весь тенант). credentials — зашифрованный JSON (cast encrypted:array), формат полей свой у каждого provider — но у wappi_pro/green_api ПУСТОЙ и не используется вовсе (см. следующий пункт), актуален только для sms_aero. webhook_token (uuid) — часть URL вебхука, им (не CSRF, вебхук идёт от внешнего сервиса без сессии — путь /webhooks/* явно исключён из CSRF в bootstrap/app.php) отличаем, к какому каналу относится входящий запрос.
    * Тенант НЕ имеет доступа к личному кабинету Wappi.Pro (корпоративный аккаунт, общий на всю платформу) — поэтому ни profile_id, ни токен тенант не вводит. Токен — App\Models\Central\PlatformSetting (central БД, ключ wappi_master_token), вносится администратором платформы в /admin/settings (Фаза 16), читается из tenant-контекста ТОЛЬКО через tenancy()->central(fn () => PlatformSetting::get(...)) — прямой Eloquent-запрос из тенантского кода попадёт не в ту БД. Профиль в Wappi при подключении канала создаёт сама система — WappiProProvider::provisionProfile() именует его "{tenant_id}-{channel_id}" (домен тенанта + id локальной записи, а не номер телефона — тот физически не известен до сканирования QR) и сначала проверяет список существующих профилей по имени (защита от дублей при ретрае после сбоя), только потом создаёт новый. При удалении канала — releaseProfile() (best-effort), чтобы отключённые номера не копились в общем аккаунте.
    * Fallback route()->name('settings.channels.retry-provision') — если provisionProfile() упал при создании канала, Channel остаётся в БД без external_profile_id (статус "Ошибка настройки" в UI), кнопка «Повторить» вызывает его снова для той же записи — не плодит новых Channel/имён профилей.
    * Chat/Message — общая схема для ДВУХ разных сценариев: type='external' (переписка с клиентом через канал — branch_id/client_id/channel_id заполнены) и type='internal' (чат сотрудников для будущего PWA — те же поля пустые, участники — таблица chat_participants, связь Chat::participants()). Один и тот же фронтенд-компонент (ChatPanel.vue) годится под оба случая. Chat НЕ имеет глобального BranchScope (внутренние чаты не должны пропадать при выбранной точке, где branch_id всегда null) — фильтрация по точке для внешних чатов делается явно в контроллере.
    * Отправка исходящего — ТОЛЬКО через SendMessageJob (очередь, Horizon) — сетевой вызов к провайдеру не должен блокировать HTTP-запрос менеджера. Статус сообщения (queued→sent/failed) обновляется по результату уже внутри job'ы.
    * Приём входящего — единый MessengerWebhookController (POST /webhooks/{provider}/{webhookToken}), сам HTTP-роут лежит в tenancy-группе routes/tenant.php (не /webhooks/* в central) — конкретный домен тенанта в URL, который выдаётся провайдеру при регистрации канала, и есть resolver тенанта, отдельная центральная таблица-указатель не нужна.
    * Broadcasting (real-time для PWA): laravel/reverb ЗАФИКСИРОВАН на 1.10.2 — см. п. 1.1. POST /broadcasting/auth и Broadcast::channel()-коллбэки (routes/channels.php) подключены вручную ВНУТРИ routes/tenant.php (Route::middleware('auth')->group(...)), а НЕ через withRouting(channels: ...) в bootstrap/app.php — иначе авторизация канала выполнялась бы без InitializeTenancyByDomain и стучалась бы в central БД, где нет chats/messages. Если понадобится ещё один Broadcast::channel(), добавляй его в routes/channels.php как обычно — это НЕ регистрационный файл маршрутов, а просто набор callback'ов, подключаемых уже из tenant-контекста.
5. КАСТОМИЗАЦИЯ (EAV) И ПРАВА (ABAC)
Гибридный EAV: Системные поля фиксированы в таблицах. Кастомные поля хранятся в custom_field_definitions и custom_field_values. Для фильтрации значения дублируются в типизированные колонки (value_text, value_number, value_date).
Динамические списки: Все таблицы (Index) строятся динамически на базе list_views (настройки колонок пользователя) и фильтруются через FieldPermissionService.
Гранулярные права (ABAC):
    * Доступ к данным (Scopes: Точки, Юрлица, Склады) вычисляется один раз при логине и кэшируется через UserScopeCachingService.
    * Приоритет прав: Индивидуальные права Пользователя (user_branches) перекрывают права Роли (role_branches).
6. КОНВЕНЦИИ И ПРАВИЛА НАПИСАНИЯ КОДА
Валидация: Всегда используй строгую валидацию ($request->validate() или Form Requests). Никогда не доверяй $request->all().
Деньги: Все денежные суммы в БД хранятся ТОЛЬКО в integer (в копейках/центах). Использование float запрещено.
Мультиязычность (Natural Language Keys): В коде Vue пиши ключи на русском: {{ $t('Добавить клиента') }}.
Переводимые модели: Из-за пакета spatie/laravel-translatable прямое обращение $model->name возвращает строку. При обновлении всегда используй $model->getTranslations('name'), иначе получишь ошибку Cannot access offset of type string on string.
Серверная пагинация: Запрещено использовать ->get() для списков. Всегда используй ->paginate(15)->withQueryString() + QueryFilterService::apply().
Асинхронность: Любой экспорт (bulkExport), массовое удаление или тяжелые операции обязаны выполняться через Laravel Horizon (Jobs).
Часовые пояса: Сервер работает в UTC. Календарный день клиента определяется часовым поясом точки (Branch::timezone) с фолбэком на пояс тенанта (Tenant::timezone, обязателен при регистрации). Любая бизнес-логика, зависящая от "какой сейчас день" (дефолтные даты операций, ночные джобы, отчеты "за сегодня/вчера", закрытие периода) — ОБЯЗАНА идти через TimezoneResolver::forBranch()/forTenant(), а не через голый now()/Carbon::today() (= UTC, не время клиента). Cron-задача, зависящая от календарного дня клиента, не может быть одним dailyAt() — см. TakeDailyAccountSnapshots (ежечасная проверка "не наступила ли полночь" по каждому используемому часовому поясу). Исключение — метки аудита (created_at, edited_at, reconciled_at и т.п.): они остаются в UTC, в локальное время зрителя их переводит браузер (toLocaleString()).
Объяснение блокировок в UI: Поле или действие, недоступное для правки (disabled), обязано объяснять пользователю причину конкретно (например: "сверено с банком — снимите отметку", "период закрыт", "системная запись, недоступна для правки"), а не просто быть серым без пояснения. Пример паттерна — lockReason() в resources/js/Pages/Finance/Transactions/Index.vue.
Право администратора на удаление без ограничений: Любой status/workflow-guard на удаление бизнес-записи (например "запись уже конвертирована в заказ-наряд", "заказ уже завершён" и т.п. — обычная проверка вида if ($model->status === 'X') { return ...withErrors(...) } перед delete()) обязан пропускать пользователя с ролью admin (User::isAdmin()) — паттерн: добавляй && !auth()->user()->isAdmin() к условию блокировки, аналогично и в bulk-удалении. В UI кнопка удаления не дизейблится для админа (только для остальных ролей, с поясняющим title — см. правило выше), а confirm()/диалог на фронте для админа обязан явно предупреждать о причине и последствиях обхода (например: "Запись уже оформлена в заказ-наряд. Удалить всё равно?"), а не просто молча удалять. Причина завести это правило: до внедрения связи Appointment↔WorkOrder (Фаза 9.4) заказы могли удаляться без отвязки записи, из-за чего в системе остались "зависшие" записи в статусе converted без реального заказа — и даже администратор не мог их удалить веб-интерфейсом, пришлось чинить точечно. Исключение — НЕ применяй этот обход к защитам целостности данных, которые не являются просто статус-меткой: сверка (is_reconciled), закрытие периода (finance_period_closures), системные справочники (Lookup.is_system), и любые операции, уже необратимо повлиявшие на склад/финансы (списанные остатки, проведённые транзакции) — там нужен явный откат через StockService/FinanceService, а не снятие блокировки.
Inertia.js & Vue: Для форм используй useForm из @inertiajs/vue3. При обновлении списков (поиск, фильтры) используй router.get(..., { preserveState: true, preserveScroll: true }).

Fluid Layout: Запрещено использовать max-w-7xl. Все контентные страницы используют w-[99%] mx-auto.
Единая навигация внутри раздела: Если у раздела больше одной связанной Index-страницы (например HR: Сотрудники/Должности/Взаиморасчёты, Settings: Точки/Юрлица/... /Зарплата), переход между ними — ОБЯЗАТЕЛЬНО общий компонент-вкладки над Header Card (паттерн SettingsNav.vue/HRNav.vue: горизонтальный <nav> из <Link>, активная — border-primary text-primary, остальные — border-transparent text-gray-500, подсветка через route().current(...)). НЕ разбрасывай переходы между такими страницами отдельными кнопками в DataTableToolbar #actions — так интерфейс выглядит по-разному в разных разделах. Tri-State Record Pattern (Паттерн 3 состояний):

    * Форма редактирования: Модальное окно по центру (<Modal>).
Бейдж Точка/Юрлицо/Направление на карточках: Любая запись с branch_id (WorkOrder, Client, Employee, Transaction и т.п.) обязана показывать точку — и, если у записи есть собственное legal_entity_id (пока только WorkOrder, см. п.4), юрлицо — и в полной карточке, и в быстром просмотре (Offcanvas/preview), а не только в списке. Видимость зеркалит философию топбара (AppHeader.vue): бейдж точки показываем, только если у тенанта больше одной точки (page.props.branches.length > 1), бейдж юрлица — только если больше одного юрлица (page.props.legal_entities.length > 1) — на одноточечном/одноюрлицом тенанте бейдж лишний шум, а не полезная информация. Готовый компонент — resources/js/Components/PointBadge.vue (принимает :branch и :legal-entity, сам решает видимость по page.props) — используй его, а не дублируй условие в каждой карточке. У записей без собственного legal_entity_id (Client/Employee/Transaction) юрлицо НЕ показывай через branch->legalEntities() "если оно одно" — это способ РЕЗОЛВИТЬ юрлицо для документа (см. DocumentPlaceholderService::resolveLegalEntity()), а не факт принадлежности самой записи; если такой записи нужен явный выбор юрлица — заводи под неё собственное nullable legal_entity_id по образцу WorkOrder, а не выводи бейдж по слепку точки. Направление (BusinessDirection) НЕ дублируй на карточках заказа/клиента/сотрудника — это концепция уровня позиции (Service.business_direction_id), не самой записи целиком (заказ может содержать позиции из разных направлений сразу, WorkOrderItem не хранит business_direction_id вообще), у неё уже есть корректное отображение на уровне каталога (Settings/Services, Settings/ServiceCategories) — попытка агрегировать её на карточку заказа даёт хрупкий и вводящий в заблуждение код. Branch/LegalEntity — SoftDeletes; на записи, ссылающиеся на удалённую точку/юрлицо (исторические заказы после удаления точки), eager-load для карточек делай через ->with(['branch' => fn ($q) => $q->withTrashed(), ...]) — иначе Eloquent применяет SoftDeletingScope даже к простому belongsTo() и бейдж молча покажет пустое значение вместо пометки "точка удалена" (PointBadge сам показывает суффикс "(удалена)"/"(удалено)" по branch.deleted_at/legalEntity.deleted_at, если они переданы через withTrashed).
История и Комментарии на полной карточке: Каждая «Полная карточка» обязана иметь вкладку «История» — системная лента событий (создание, смена статуса, оплата, привязка связанной записи и т.п.), пишется ВРУЧНУЮ через App\Services\ActivityLogger::log() в конкретных точках контроллеров человеческим текстом на русском. НЕ используй автологирование диффов полей (пакетный LogsActivity trait) — оно даёт нечитаемый технический шум вида «branch_id изменён с 3 на 5» вместо осмысленного «Заказ создан из записи в календаре». Комментарии и заметки менеджеров — ОБЯЗАТЕЛЬНО отдельная вкладка «Комментарии», никогда не смешивай с «Историей»: если несколько менеджеров параллельно комментируют, общая лента превращается в кашу, где не видно ни системных событий, ни обсуждения. Технически оба используют одну и ту же таблицу activity_log (пакет spatie/laravel-activitylog, миграция в database/migrations/tenant/ — это данные тенанта, не landlord), просто разные выборки на бэкенде по полю event (event='comment' — в «Комментарии», всё остальное — в «Историю») и один и тот же фронтенд-компонент <ActivityTimeline> (resources/js/Components/ActivityTimeline.vue), с полем ввода комментария только во вкладке «Комментарии» (проп comment-url). Модель подключает связь через трейт HasActivityLog (app/Models/Concerns/), а не через LogsActivity пакета. Ссылки на связанные записи внутри события — через properties.links (массив {type,id,label}), не парсинг ссылок из текста. Эталонная реализация — WorkOrderController + WorkOrders/Show.vue.
Roll-up Истории на карточках Клиента/Автомобиля: Их лента дополнительно подтягивает события WorkOrder/Appointment, у которых properties.client_id/vehicle_id указывает на эту запись — ActivityLogger::log() САМ копирует client_id/vehicle_id из $subject (если такие атрибуты у него есть), передавать их вручную на каждом вызове не нужно; запрос — ActivityLogger::feedFor($subject, $rollupField).
Точность текста события ОБЯЗАТЕЛЬНА: Событие может показываться не только в «Истории» своей записи, но и через roll-up в ленте другой (Заказ → лента Клиента/Автомобиля) — там неявный контекст страницы («мы сейчас внутри Заказа №12») теряется. Поэтому текст описания сам по себе обязан однозначно называть конкретную запись, к которой относится (номер заказа, дата и т.п.) — «Статус заказа №12 изменён на «Готов»», а не безличное «Статус изменён на «Готов»». Компоненты: Обязательно использование <DataTableToolbar> (поиск), <Pagination>, <BulkActions> (массовые операции) и <PageHelper> (сворачиваемые подсказки).

Полосатые таблицы (zebra): Каждая строка <tr> в <tbody> любой таблицы (кроме заведомо однострочных/коротких списков без нужды в ней) обязана иметь odd:bg-gray-100/80 dark:odd:bg-gray-800/40 в дополнение к hover:bg-gray-50/50 dark:hover:bg-gray-800/30 — так строки визуально не сливаются. Это работает через CSS :nth-child(odd), поэтому корректно даже в перетаскиваемых (vuedraggable) таблицах — JS ничего вручную не считает.

Короткие фиксированные списки (2-6 вариантов — статусы, типы, да/нет) можно оставлять обычным <select>, поиск там не нужен. 9. ПРАВИЛО ВЫВОДА КОДА (ACM - Absolute Character Match)

Это самое важное правило при генерации кода:
При внесении изменений в существующий файл, ты ОБЯЗАН вывести весь файл целиком, от первой до последней строки, побайтово совпадающим с оригиналом в тех местах, которые не подвергались изменениям.
Любые сокращения, удаление пустых строк, переформатирование нетронутого кода или использование плейсхолдеров — КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ. Если файл слишком длинный, разбей его вывод на несколько сообщений, но не сокращай код.
Практически (через Edit/Write): перед Write, заменяющим содержимое существующего файла, убедись, что новое содержимое не короче оригинала без явной причины (удаление кода должно быть осознанным, не побочным эффектом усечения). Один из прошлых экспериментов с локальным AI-агентом в этом проекте закончился заменой всего routes/tenant.php на 4 строки вместо добавления одного маршрута — именно этот сценарий и запрещает данное правило.

📅 Фаза 9: Календарь и Запись (Appointments & Scheduling) — реализовано

Не смешивать: правки/отмены/переносы Appointment не должны требовать отката складских или финансовых операций, потому что до конвертации их попросту нет.

📄 Фаза 12: Документооборот (Document Management) — реализовано
Генерация печатных форм (Акты, Счета, Договоры) из шаблонов с плейсхолдерами, для любой сущности (ядро: work_order/transaction/client, расширяется добавлением записи в реестр — см. ниже).
    * 12.1. Конструктор шаблонов — Settings/DocumentTemplates (App\Http\Controllers\Tenant\DocumentTemplateController::ENTITY_TYPES — реестр сущностей, аналог MessageTemplateController::TRIGGERS). Плейсхолдеры — {{ключ}} + ОДНА неглубокая табличная секция {{#items}}...{{/items}}, рендерится App\Services\Documents\DocumentRenderer — НЕ Blade::render() (тело шаблона редактирует тенант-админ, Blade дал бы выполнение PHP через @php — критично на мультитенантной платформе). Источник данных — App\Services\Documents\DocumentPlaceholderService::buildFor() (реквизиты юрлица — LegalEntity.requisites JSON + Account.is_default_for_invoicing, точка — Branch).
    * 12.2. Генерация — App\Services\Documents\DocumentGenerationService::generate(), синхронно (не через Horizon — единичный документ не bulk-операция из CLAUDE.md п.6). Номер — App\Services\Documents\DocumentNumerator, атомарный (DB::transaction + lockForUpdate на document_numerators), НЕ COUNT(*)+1 — пропуски номеров при удалении документа в общем случае штатны (как в Bitrix24/1С). Нумерация — отдельно на каждую связку (юрлицо, шаблон), year=0 сентинел вместо null, если у шаблона number_reset_yearly=false (NULL в unique-индексе MySQL не считается дублем сам с собой — год=0 гарантирует один нумератор на связку). Удаление — DocumentController::destroy() (Document — SoftDeletes), по явному запросу владельца платформы номер при этом переиспользуется: DocumentNumerator::reclaimIfLast() откатывает last_number на 1 назад, ТОЛЬКО если удаляемый документ — самый свежий выданный номер своей связки (сравнение по отформатированной строке, не по id) — типичный кейс "сформировал по ошибке, сразу удалил" не оставляет дыру. Документ, удалённый не по порядку (уже есть более новые), номер не возвращает — дыра в этом случае неизбежна и корректна, иначе разъехались бы номера документов, выданных после него.
    * 12.3. PDF — barryvdh/laravel-dompdf (чистый PHP, без Node/Chromium; default_font переключён в config/dompdf.php на 'DejaVu Sans' — дефолтный 'serif' не содержит кириллицы вообще). Файл хранится через spatie/laravel-medialibrary (Document::class implements HasMedia, коллекция 'file') на диске 'local' (НЕ 'public' пакета по умолчанию — документы содержат финансовые/персональные данные, публичной ссылкой по предсказуемому пути раздавать нельзя, скачивание только через DocumentController::download() с BranchScope). Раздел «Документы» (documents.index) — реестр со списком/фильтрами (тип шаблона/сущности/юрлица/период) — сайдбар-модуль 'documents' уже сидировался (ModuleSeeder), был скрыт до этой фазы тем же механизмом, что открыл «Общение» в Фазе 11. Генерация доступна и оттуда, и с карточек записи (вкладка «Документы» — WorkOrders/Show.vue, CRM/Clients/Show.vue).
    * 12.4. Конструктор шаблонов — визуальный редактор (Tiptap, @tiptap/vue-3) с переключением в HTML-код, плюс загрузка готового .docx: DocumentTemplate.format='docx' → App\Services\Documents\DocxToHtmlConverter конвертирует файл в HTML ОДИН РАЗ при сохранении (PhpWord IOFactory::load() + HTML Writer, чистый PHP, БЕЗ LibreOffice) — дальше это обычный html-шаблон, DocumentGenerationService не знает и не ветвится по происхождению. Табличная секция для .docx-шаблонов размечается НЕ маркерами {{#items}}/{{/items}} (в Word их некуда вписать ровно на границе строки таблицы) — DocumentRenderer сам находит <tr>, содержащий первый плейсхолдер секции (например {{item.name}}), и клонирует именно эту строку; тот же фолбэк молча работает и для html-шаблонов, если явных маркеров нет.
    * 12.5. Кириллица в PDF — НЕ полагайся только на config/dompdf.php default_font='DejaVu Sans': это фолбэк, применяемый лишь когда font-family вообще не задан в HTML. Если тело шаблона (написанное вручную ИЛИ полученное из .docx — Word всегда проставляет свой font-family типа Calibri/Times New Roman в экспортированном HTML) указывает любой другой font-family, dompdf резолвит его через vendor/dompdf/dompdf/lib/fonts/installed-fonts.dist.json в один из Base-14 PDF-шрифтов (Arial/sans-serif → Helvetica) — а у них нет кириллических глифов вообще, без единой ошибки на любом этапе, просто "?" вместо букв на готовой странице. Поэтому DocumentRenderer::render() принудительно вставляет `<style>*{font-family:"DejaVu Sans",sans-serif !important}</style>` в начало итогового HTML перед рендером в PDF — не убирай это без замены на другой механизм гарантированной кириллицы. Там же — safety-net: неподставленный `{{ключ}}` (типичный случай — {{legal_entity.kpp}} у ИП, там просто нет такого ключа в requisites, в отличие от ООО) вырезается регэкспом после рендера, чтобы сырой плейсхолдер физически не мог попасть в документ, уходящий клиенту.
    * 12.6. Документ — зафиксированный во времени артефакт, НЕ живая проекция связанной записи: сгенерированный PDF никогда не перерисовывается сам по себе при изменении заказа/клиента задним числом (иначе то, что уже реально отправили клиенту, могло бы молча "переписаться"). Вместо этого — Document::isStale() (аксессор is_stale, требует заранее eager-loaded documentable + branch.legalEntity — НЕ через $appends глобально, точечно через ->append('is_stale') в DocumentController::index()/WorkOrderController::show()/ClientController::show(), иначе N+1) сравнивает created_at документа с updated_at связанной записи и юрлиц точки-источника — если новее, в UI рядом с номером документа предупреждающая иконка. Пользователю — выбор из двух действий: DocumentController::regenerateAsNew() формирует НОВЫЙ документ (новый номер через тот же DocumentNumerator) с текущими данными, старый не удаляет, а помечает superseded_by_document_id (FK nullOnDelete — если новый документ потом удалят, старый сам вернётся в обычное "устарел") — в UI такой старый документ показывается серой неактивной пометкой "заменён", а не активным предупреждением; DocumentController::replace() — то же самое содержимое, но БЕЗ нового номера (DocumentGenerationService::replace() не обращается к DocumentNumerator), тот же id/номер, только created_at и файл обновляются — для случая "просто исправить уже выпущенный документ", когда отдельная запись в истории не нужна.
    * 12.7. Подписанты для блока подписи в печатных формах ("Поставщик ___ подпись ___") — CountryConfigService::signatorySchema() (должность/ФИО руководителя и бухгалтера), НЕ часть requisite_schema (та — налоговые номера, разные по странам) и не зависит от юрисдикции, поэтому один список, подмешивается в getForCountry()['signatory_schema'] и рендерится тем же паттерном "динамическая схема → requisites JSON", что и requisite_schema — сразу в ДВУХ формах: Settings/LegalEntities/Index.vue (юрлицо тенанта) и CRM/Clients/Index.vue (B2B-клиент — сам сторона сделки в договоре, вкладка «Реквизиты» при type=b2b). DocumentPlaceholderService уже разворачивает ВСЕ ключи requisites как {{legal_entity.*}}/{{client.*}} — новый код для рендера не понадобился, только добавление ключей в форму + DocumentTemplateController::COMMON_PLACEHOLDERS/CLIENT_ORGANIZATION_PLACEHOLDERS для подсказки в конструкторе шаблонов.

WorkOrderController::processPayment() начисляет client.bonus_points при оплате НЕ бонусным счётом — cashback_percent грейда клиента × сумма платежа, конвертация рублей в баллы через тот же курс bonus_rub_per_point (Settings/CRM), что и при списании (п.14.2) — умышленно НЕ начисляется на оплату самими бонусами, иначе баллы начислялись бы сами на себя.

Агрегаты — withCount/withMax/withSum (SQL-подзапросы, без ->get() по списку — CLAUDE.md п.6), классификация — уже после пагинации по готовым числам страницы (classify()); для карточки одного клиента — classifyFromCounts() по уже загруженной коллекции заказов (без второго запроса). Фильтр по сегменту в CRM/Clients — ClientSegmentService::applyFilter() через HAVING на тех же алиасах (не обычная колонка, обрабатывается в контроллере отдельно от QueryFilterService, который иначе сделал бы наивный WHERE segment = ...) — ВАЖНО: закрывающий having-callback для составных условий (`having(fn (Illuminate\Database\Query\Builder $q) => ...)`) обязан использовать havingNull()/orHaving(), а НЕ whereNull()/orWhere() — closure получает Query\Builder, но добавление через where-методы попадает в $wheres, а не в $havings, и HAVING-условие молча остаётся пустым (было живым багом здесь: сегмент "Новичок" пересекался со "Спящим", т.к. фильтр "новичков" не проверял давность — нашлось только прогоном через реальные пересекающиеся тестовые данные, не чтением кода).

🛠 Фаза 16: Платформенная админка (Central Admin)
Фундамент заложен при внедрении автопровижининга Wappi.Pro (см. п.4) — понадобилось где-то безопасно хранить общий на всю платформу токен, а до этого central-аутентификации в системе не было вообще. Построено именно как фундамент под полноценную будущую админку (осознанное решение владельца — "нужен фундамент для админки всей СРМ и всех тенантов с отслеживанием их данных"), не как разовая заглушка под один токен.
    * Готово — central-гвард 'platform_admin' (config/auth.php), отдельный от тенантского 'web' (App\Models\Central\PlatformAdmin, central БД, НЕ переиспользует App\Models\User). Заводится только через artisan platform:create-admin — публичной регистрации нет.
    * Готово — /admin/tenants: список тенантов с базовыми показателями (кол-во пользователей/точек/клиентов/заказ-нарядов, дата последней активности), синхронный обход через $tenant->run() — нормально при текущем малом числе тенантов.
    * Готово — /admin/settings: общеплатформенные настройки (App\Models\Central\PlatformSetting, ключ/значение, value зашифровано) — пока один ключ wappi_master_token, список ключей зашит явно в PlatformSettingController::KEYS (не заводи там ключ, который реально никто не читает).
    * НЕ этой поставки (будущие итерации поверх фундамента): биллинг, детальная аналитика/мониторинг по тенантам, impersonation, управление тарифами/лимитами. Если тенантов станет много — обход в TenantController нужно будет вынести в кэш/очередь (сейчас синхронный ради простоты).
    * ВАЖНО: тенантский User.isAdmin() — это руководитель конкретного бизнеса (полный доступ к своим пользовательским функциям), а НЕ администратор платформы. Никогда не показывай/не давай доступ к central-админке (`/admin/*`) на основании тенантского isAdmin или любого другого тенантского признака — гарантированно правильного способа отличить "владелец бизнеса" от "оператор платформы" изнутри тенантского контекста нет (разные guard'ы, разные БД). Даже ссылку-ярлык на `/admin/login` в тенантском интерфейсе показывать не нужно — глобальный администратор заходит на central-домен напрямую.
