0. КЛЮЧЕВОЙ АРХИТЕКТУРНЫЙ ПРИНЦИП (ЧИТАТЬ ПЕРВЫМ)

Это SaaS-платформа, а не просто CRM.

Tenant (Тенант) — это компания-клиент. У каждого тенанта своя физическая база данных (Database-per-Tenant, пакет stancl/tenancy).
Branch (Филиал) — физический адрес внутри тенанта. Один тенант может иметь много филиалов.
Core (Ядро) — общий код платформы. Любая кастомизация тенанта (кастомные поля, формы) живет рядом с ядром в БД тенанта, а не меняет таблицы ядра.
Изоляция: Любая сущность, запрос, кеш-ключ или очередь обязаны быть в контексте конкретного тенанта. Забытый tenant-scope = утечка данных между компаниями. Это критический баг.
1. WORKFLOW АГЕНТА И ИНСТРУМЕНТЫ (TOOLS)

Твоя автономная работа строго регламентирована. Для задач, изменяющих код, правильная последовательность действий:

createBranch — ВСЕГДА вызывай первым шагом для создания feature-ветки.
readFile — прочитай существующий файл, если собираешься его менять.
writeDiff — предложи изменение. ВНИМАНИЕ: newContent должен содержать ПОЛНОЕ новое содержимое файла, а не только измененный кусок. Замена файла на сокращенный контент — критическая ошибка.
Ожидание человека — writeDiff только сохраняет черновик (patch). Он НЕ коммитит код. После вызова writeDiff заверши свой ответ и попроси человека применить патч командой php artisan agent:apply-patch.
createPullRequest — вызывай ТОЛЬКО после того, как человек подтвердит, что патч применен и закоммичен.
2. КОМАНДЫ И ЗАПУСК (CLI)
Запуск проекта: php artisan serve (бэкенд) и npm run dev (фронтенд Vite). Домены маршрутизируются через dnsmasq (например, *.localhost).
Миграции ядра (Landlord DB): php artisan migrate
Миграции тенантов (Client DBs): php artisan tenants:migrate (применяет миграции из database/migrations/tenant ко всем базам).
Сидирование тенантов: php artisan tenants:seed
Тестирование (Tenant-aware): php artisan test --configuration=phpunit.tenant.xml (использует изолированную sandbox-БД тенанта tenant_agent_sandbox). Обычный php artisan test гоняет тесты центральной логики.
Тесты (PHPUnit 12): Используй атрибут #[Test] из PHPUnit\Framework\Attributes\Test или префикс test в названии метода. Doc-comment @test больше не поддерживается.
3. АРХИТЕКТУРА И РАСПОЛОЖЕНИЕ ФАЙЛОВ
Контроллеры Тенанта: app/Http/Controllers/Tenant/ — 95% бизнес-логики.
Контроллеры Центральные: app/Http/Controllers/Central/ — регистрация, лендинг, биллинг.
Модели: app/Models/. Центральные модели (Tenant, Domain) наследуют классы tenancy. Остальные — обычные модели.
Сервисы: app/Services/ — вся сложная бизнес-логика (QueryFilterService, BranchContext, StockService, FinanceService).
Фронтенд: resources/js/Pages/ (страницы) и resources/js/Components/ (переиспользуемые UI-элементы).
Миграции: database/migrations/ (центральные) и database/migrations/tenant/ (тенанты).
Роутинг: Маршруты тенанта (бизнес-логика) лежат строго в routes/tenant.php. Маршруты лендинга/центральной БД — в routes/web.php.
4. БИЗНЕС-ЛОГИКА И СУЩНОСТИ
Филиал (Branch) vs Юрлицо (Legal Entity):
    * Филиал — операционная логика (Сотрудники, Расписание, Склады, Заказы).
    * Юрлицо — исключительно финансовый профиль (Кассы, Реквизиты для документов).
Склад и Типы учета:
    * Режимы склада: per_branch (раздельный), shared (общий), mixed (смешанный). Резолвинг склада идет через WarehouseResolver.
    * Типы учета товаров: average (средневзвешенный для химии) и batch (партионный/FIFO для дорогих пленок).
Универсальные справочники (Lookups):
    * Простые списки (источники клиентов, типы кузова) хранятся в единой таблице lookups. На фронте используется компонент <CreatableSelect> для добавления на лету.
5. КАСТОМИЗАЦИЯ (EAV) И ПРАВА (ABAC)
Гибридный EAV: Системные поля фиксированы в таблицах. Кастомные поля хранятся в custom_field_definitions и custom_field_values. Для фильтрации значения дублируются в типизированные колонки (value_text, value_number, value_date).
Динамические списки: Все таблицы (Index) строятся динамически на базе list_views (настройки колонок пользователя) и фильтруются через FieldPermissionService.
Гранулярные права (ABAC):
    * Доступ к данным (Scopes: Филиалы, Юрлица, Склады) вычисляется один раз при логине и кэшируется через UserScopeCachingService.
    * Приоритет прав: Индивидуальные права Пользователя (user_branches) перекрывают права Роли (role_branches).
6. КОНВЕНЦИИ И ПРАВИЛА НАПИСАНИЯ КОДА
Валидация: Всегда используй строгую валидацию ($request->validate() или Form Requests). Никогда не доверяй $request->all().
Деньги: Все денежные суммы в БД хранятся ТОЛЬКО в integer (в копейках/центах). Использование float запрещено.
Мультиязычность (Natural Language Keys): В коде Vue пиши ключи на русском: {{ $t('Добавить клиента') }}.
Переводимые модели: Из-за пакета spatie/laravel-translatable прямое обращение $model->name возвращает строку. При обновлении всегда используй $model->getTranslations('name'), иначе получишь ошибку Cannot access offset of type string on string.
Серверная пагинация: Запрещено использовать ->get() для списков. Всегда используй ->paginate(15)->withQueryString() + QueryFilterService::apply().
Асинхронность: Любой экспорт (bulkExport), массовое удаление или тяжелые операции обязаны выполняться через Laravel Horizon (Jobs).
Inertia.js & Vue: Для форм используй useForm из @inertiajs/vue3. При обновлении списков (поиск, фильтры) используй router.get(..., { preserveState: true, preserveScroll: true }).
7. UI/UX ДИЗАЙН-СИСТЕМА (ATTEX THEME)
Fluid Layout: Запрещено использовать max-w-7xl. Все контентные страницы используют w-[99%] mx-auto.
Tri-State Record Pattern (Паттерн 3 состояний):
    * Быстрый просмотр: Выезжающая панель справа (<Offcanvas>) при клике на строку таблицы.
    * Полная карточка: Отдельная страница (/crm/clients/{id}) с KPI-дашбордом и таймлайном.
    * Форма редактирования: Модальное окно по центру (<Modal>).
Компоненты: Обязательно использование <DataTableToolbar> (поиск), <Pagination>, <BulkActions> (массовые операции) и <PageHelper> (сворачиваемые подсказки).
Dark Mode: Вся верстка обязана поддерживать темную тему через префикс dark: (например, bg-white dark:bg-[#313a46]).
8. "ПОДВОДНЫЕ КАМНИ" (СТРОГИЕ ЗАПРЕТЫ)
🚫 Никогда не трогай файлы в vendor/.
🚫 Никогда не удаляй системные колонки (DROP COLUMN). Если поле не нужно, оно скрывается на уровне UI. Миграции ядра должны быть идемпотентны.
🚫 Не делай хардкод ID филиалов или юрлиц. Используй BranchContext::current().
🚫 Не делай глобальных запросов к БД без учета тенанта.
🚫 Не используй синхронный провижининг. Создание тенанта идет через цепочку ProvisionTenantPipeline в очередях.
🚫 Никакой лени. Не используй комментарии вида // остальной код без изменений.
9. ПРАВИЛО ВЫВОДА КОДА (ACM - Absolute Character Match)

Это самое важное правило при генерации кода:
При внесении изменений в существующий файл, ты ОБЯЗАН вывести весь файл целиком, от первой до последней строки, побайтово совпадающим с оригиналом в тех местах, которые не подвергались изменениям.
Любые сокращения, удаление пустых строк, переформатирование нетронутого кода или использование плейсхолдеров — КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ. Если файл слишком длинный, разбей его вывод на несколько сообщений, но не сокращай код.
