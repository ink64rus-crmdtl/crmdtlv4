0. КЛЮЧЕВОЙ АРХИТЕКТУРНЫЙ ПРИНЦИП (ЧИТАТЬ ПЕРВЫМ)

Это SaaS-платформа, а не просто CRM.

Tenant (Тенант) — это компания-клиент. У каждого тенанта своя физическая база данных (Database-per-Tenant, пакет stancl/tenancy).
Branch (Филиал) — физический адрес внутри тенанта. Один тенант может иметь много филиалов.
Core (Ядро) — общий код платформы. Любая кастомизация тенанта (кастомные поля, формы) живет рядом с ядром в БД тенанта, а не меняет таблицы ядра.
Изоляция: Любая сущность, запрос, кеш-ключ или очередь обязаны быть в контексте конкретного тенанта. Забытый tenant-scope = утечка данных между компаниями. Это критический баг.
1. WORKFLOW АГЕНТА И ИНСТРУМЕНТЫ (TOOLS)

Твоя автономная работа строго регламентирована. Для задач, изменяющих код, правильная последовательность действий:

Read — прочитай существующий файл, если собираешься его менять.
Edit/Write — вноси изменения напрямую в рабочую копию (working tree). Edit — точечная правка (diff), Write — только для новых файлов или полной перезаписи. Отдельного шага "сохранить черновик" и ожидания применения патча человеком не существует — изменения сразу оказываются в файловой системе проекта.
Bash — используй для проверки (php -l, npx vite build, php artisan test), для git-операций и для любых shell-команд.
Git commit — НИКОГДА не коммить самостоятельно, если человек явно не попросил ("закоммить изменения" и т.п.). Внесённые правки остаются в рабочей копии как незакоммиченные изменения до отдельного явного запроса.
Ветки — не создавай feature-ветки автоматически; работай в той ветке, что уже активна, если человек явно не попросил создать новую.
Pull Request — создавай (gh pr create) ТОЛЬКО по явной просьбе человека, и только после того, как изменения закоммичены.
2. КОМАНДЫ И ЗАПУСК (CLI)
Запуск проекта: php artisan serve (бэкенд) и npm run dev (фронтенд Vite). Домены маршрутизируются через dnsmasq (например, *.localhost).
Миграции ядра (Landlord DB): php artisan migrate
Миграции тенантов (Client DBs): php artisan tenants:migrate (применяет миграции из database/migrations/tenant ко всем базам).
Сидирование тенантов: php artisan tenants:seed
Тестирование (Tenant-aware): php artisan test --configuration=phpunit.tenant.xml (использует изолированную sandbox-БД тенанта tenant_agent_sandbox). Обычный php artisan test гоняет тесты центральной логики.
Тесты (PHPUnit 12): Используй атрибут #[Test] из PHPUnit\Framework\Attributes\Test или префикс test в названии метода. Doc-comment @test больше не поддерживается.
3. АРХИТЕКТУРА И РАСПОЛОЖЕНИЕ ФАЙЛОВ
Контроллеры Тенанта: app/Http/Controllers/Tenant/ — 95% бизнес-логики.
Контроллеры Центральные: app/Http/Controllers/Central/ — регистрация, лендинг, биллинг.
Модели: app/Models/. Центральные модели (Tenant, Domain) наследуют классы tenancy. Остальные — обычные модели.
Сервисы: app/Services/ — вся сложная бизнес-логика (QueryFilterService, BranchContext, StockService, FinanceService).
Фронтенд: resources/js/Pages/ (страницы) и resources/js/Components/ (переиспользуемые UI-элементы).
Миграции: database/migrations/ (центральные) и database/migrations/tenant/ (тенанты).
Роутинг: Маршруты тенанта (бизнес-логика) лежат строго в routes/tenant.php. Маршруты лендинга/центральной БД — в routes/web.php.
4. БИЗНЕС-ЛОГИКА И СУЩНОСТИ
Филиал (Branch) vs Юрлицо (Legal Entity):
    * Филиал — операционная логика (Сотрудники, Расписание, Склады, Заказы).
    * Юрлицо — исключительно финансовый профиль (Кассы, Реквизиты для документов).
Склад и Типы учета:
    * Режимы склада: per_branch (раздельный), shared (общий), mixed (смешанный). Резолвинг склада идет через WarehouseResolver.
    * Типы учета товаров: average (средневзвешенный для химии) и batch (партионный/FIFO для дорогих пленок).
Универсальные справочники (Lookups):
    * Простые списки (источники клиентов, типы кузова) хранятся в единой таблице lookups. На фронте используется компонент <CreatableSelect> для добавления на лету.
Финансы (Accounts / Transactions):
    * Счета (Account) бывают 4 типов: cash (касса), bank (расчетный счет), acquiring (эквайринг, имеет commission_percent), bonus (единственный системный виртуальный счет тенанта для оплаты бонусами клиента — не привязан к юрлицу, не редактируется через обычную форму счетов).
    * Любое изменение Account.balance — ТОЛЬКО через FinanceService (processTransaction/processTransfer/updateTransaction/revertTransaction). Никогда не трогай balance напрямую в контроллере.
    * У Transaction есть transaction_date (бизнес-дата операции, редактируется, можно вносить задним числом) отдельно от created_at (техническая метка создания записи, никогда не меняется).
    * Редактирование транзакции — O(1) пересчет баланса счета дельтой (новая сумма минус старая), а не полный пересчет по истории.
    * Сверка (is_reconciled) блокирует правку суммы/даты, пока не снята. Закрытие периода (finance_period_closures, PeriodClosureService::assertNotClosed) блокирует создание/правку/отмену операций с датой не позже границы закрытия — обе проверки живут внутри FinanceService, не дублируй их в контроллерах.
    * Дневные снэпшоты остатков (account_daily_snapshots, AccountSnapshotService) считаются независимо по каждой дате (не цепочкой от предыдущего дня).
5. КАСТОМИЗАЦИЯ (EAV) И ПРАВА (ABAC)
Гибридный EAV: Системные поля фиксированы в таблицах. Кастомные поля хранятся в custom_field_definitions и custom_field_values. Для фильтрации значения дублируются в типизированные колонки (value_text, value_number, value_date).
Динамические списки: Все таблицы (Index) строятся динамически на базе list_views (настройки колонок пользователя) и фильтруются через FieldPermissionService.
Гранулярные права (ABAC):
    * Доступ к данным (Scopes: Филиалы, Юрлица, Склады) вычисляется один раз при логине и кэшируется через UserScopeCachingService.
    * Приоритет прав: Индивидуальные права Пользователя (user_branches) перекрывают права Роли (role_branches).
6. КОНВЕНЦИИ И ПРАВИЛА НАПИСАНИЯ КОДА
Валидация: Всегда используй строгую валидацию ($request->validate() или Form Requests). Никогда не доверяй $request->all().
Деньги: Все денежные суммы в БД хранятся ТОЛЬКО в integer (в копейках/центах). Использование float запрещено.
Мультиязычность (Natural Language Keys): В коде Vue пиши ключи на русском: {{ $t('Добавить клиента') }}.
Переводимые модели: Из-за пакета spatie/laravel-translatable прямое обращение $model->name возвращает строку. При обновлении всегда используй $model->getTranslations('name'), иначе получишь ошибку Cannot access offset of type string on string.
Серверная пагинация: Запрещено использовать ->get() для списков. Всегда используй ->paginate(15)->withQueryString() + QueryFilterService::apply().
Асинхронность: Любой экспорт (bulkExport), массовое удаление или тяжелые операции обязаны выполняться через Laravel Horizon (Jobs).
Часовые пояса: Сервер работает в UTC. Календарный день клиента определяется часовым поясом филиала (Branch::timezone) с фолбэком на пояс тенанта (Tenant::timezone, обязателен при регистрации). Любая бизнес-логика, зависящая от "какой сейчас день" (дефолтные даты операций, ночные джобы, отчеты "за сегодня/вчера", закрытие периода) — ОБЯЗАНА идти через TimezoneResolver::forBranch()/forTenant(), а не через голый now()/Carbon::today() (= UTC, не время клиента). Cron-задача, зависящая от календарного дня клиента, не может быть одним dailyAt() — см. TakeDailyAccountSnapshots (ежечасная проверка "не наступила ли полночь" по каждому используемому часовому поясу). Исключение — метки аудита (created_at, edited_at, reconciled_at и т.п.): они остаются в UTC, в локальное время зрителя их переводит браузер (toLocaleString()).
Объяснение блокировок в UI: Поле или действие, недоступное для правки (disabled), обязано объяснять пользователю причину конкретно (например: "сверено с банком — снимите отметку", "период закрыт", "системная запись, недоступна для правки"), а не просто быть серым без пояснения. Пример паттерна — lockReason() в resources/js/Pages/Finance/Transactions/Index.vue.
Inertia.js & Vue: Для форм используй useForm из @inertiajs/vue3. При обновлении списков (поиск, фильтры) используй router.get(..., { preserveState: true, preserveScroll: true }).
7. UI/UX ДИЗАЙН-СИСТЕМА (ATTEX THEME)
Fluid Layout: Запрещено использовать max-w-7xl. Все контентные страницы используют w-[99%] mx-auto.
Tri-State Record Pattern (Паттерн 3 состояний):
    * Быстрый просмотр: Выезжающая панель справа (<Offcanvas>) при клике на строку таблицы.
    * Полная карточка: Отдельная страница (/crm/clients/{id}) с KPI-дашбордом и таймлайном.
    * Форма редактирования: Модальное окно по центру (<Modal>).
Компоненты: Обязательно использование <DataTableToolbar> (поиск), <Pagination>, <BulkActions> (массовые операции) и <PageHelper> (сворачиваемые подсказки).
Dark Mode: Вся верстка обязана поддерживать темную тему через префикс dark: (например, bg-white dark:bg-[#313a46]).
Выпадающие списки с поиском: Для любого select, где список вариантов реально длинный и растёт со временем (клиенты, автомобили, сотрудники, филиалы, услуги/товары, посты, справочники и т.п.) — ОБЯЗАТЕЛЬНО используй <SearchableSelect> (resources/js/Components/SearchableSelect.vue) вместо голого <select>. Короткие фиксированные списки (2-6 вариантов — статусы, типы, да/нет) можно оставлять обычным <select>, поиск там не нужен. Это правило действует и для уже существующих select — переводи их на SearchableSelect по ходу любой правки затрагиваемой страницы, не обязательно отдельной задачей.

9. ПРАВИЛО ВЫВОДА КОДА (ACM - Absolute Character Match)

Это самое важное правило при генерации кода:
При внесении изменений в существующий файл, ты ОБЯЗАН вывести весь файл целиком, от первой до последней строки, побайтово совпадающим с оригиналом в тех местах, которые не подвергались изменениям.
Любые сокращения, удаление пустых строк, переформатирование нетронутого кода или использование плейсхолдеров — КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ. Если файл слишком длинный, разбей его вывод на несколько сообщений, но не сокращай код.
Практически (через Edit/Write): перед Write, заменяющим содержимое существующего файла, убедись, что новое содержимое не короче оригинала без явной причины (удаление кода должно быть осознанным, не побочным эффектом усечения). Один из прошлых экспериментов с локальным AI-агентом в этом проекте закончился заменой всего routes/tenant.php на 4 строки вместо добавления одного маршрута — именно этот сценарий и запрещает данное правило.

📅 Фаза 9: Календарь и Запись (Appointments & Scheduling)
Детейлинг и мойка не могут работать без удобного планировщика загрузки постов и мастеров.
Архитектурное решение (зафиксировано): Appointment и WorkOrder — раздельные сущности, гибридная схема. Appointment — это намерение/бронь (клиент, авто, филиал, время), не трогает склад и финансы. Appointment может иметь необязательные AppointmentItem (услуга + ориентировочная цена) — только для предварительной сметы клиенту, без резервирования остатков и без движения по счетам. WorkOrder создаётся только по факту приезда клиента (конвертация, 9.4) — именно WorkOrder остаётся единственным триггером для склада (StockService), финансов (FinanceService) и будущего payroll (10.2, начисление на completed). Не смешивать: правки/отмены/переносы Appointment не должны требовать отката складских или финансовых операций, потому что до конвертации их попросту нет.
    * 9.1. Интеграция календаря: Внедрение @fullcalendar/vue3 для визуального отображения записей.
    * 9.2. CRUD Записей (Appointments): Управление таблицами appointments и appointment_items. Привязка записи к Клиенту, Автомобилю, Филиалу и конкретному времени (start_at, end_at).
    * 9.3. Управление загрузкой (Capacity Management): Визуальное разделение по постам/боксам.
    * 9.4. Конвертация: Бесшовная конвертация Записи (Appointment) в Заказ-наряд (Work Order) при приезде клиента — AppointmentItem копируются в WorkOrderItem как стартовые позиции.

💰 Фаза 10: Мотивация и Зарплата (Payroll & HR)
В карточке сотрудника уже зарезервирована вкладка "Зарплата". Пора её оживить.
    * 10.1. Правила начисления (Payroll Rules): Настройка таблицы payroll_rules. Задание окладов, процента от стоимости услуги (например, 40% за полировку) или фиксированной ставки за выезд.
    * 10.2. Автоматические начисления: При переводе Заказ-наряда в статус completed, система должна автоматически создавать записи в payrolls (тип accrual) для мастеров, указанных в позициях заказа.
    * 10.3. Выплаты и штрафы: Ручное создание премий, штрафов (deduction) и выплата ЗП (payout) с привязкой к кассе (создание транзакции expense).
    * 10.4. Взаиморасчеты с сотрудниками: Отчет по балансу каждого сотрудника.

📊 Фаза 13: Аналитика и Отчетность (Analytics & Reports)
Сбор данных для владельца бизнеса.
    * 13.1. Финансовый отчет (P&L / CashFlow): Сводка по доходам и расходам в разрезе статей (transaction_categories) и филиалов.
    * 13.2. Аналитика по клиентам: Расчет LTV (Lifetime Value), частоты визитов, оттока (Churn rate). Оживление KPI-дашборда в карточке клиента.
    * 13.3. Складская аналитика: Отчеты по оборачиваемости товаров, неликвидам, маржинальности материалов.
    * 13.4. Выработка мастеров: Отчет по выработке нормо-часов и принесенной прибыли по каждому сотруднику.

🎁 Фаза 14: Программа лояльности и Маркетинг
Работа с LTV и возвратом клиентов.
    * 14.1. Бонусная система: Автоматическое начисление кэшбека (в clients.bonus_points) при оплате заказа в зависимости от грейда клиента (client_groups).
    * 14.2. Оплата бонусами: Возможность частичной оплаты Заказ-наряда накопленными баллами.
    * 14.3. Сегментация: RFM-анализ (Recency, Frequency, Monetary) для выделения "Спящих", "Лояльных" и "Новичков".
