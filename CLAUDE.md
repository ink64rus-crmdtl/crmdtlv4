0. КЛЮЧЕВОЙ АРХИТЕКТУРНЫЙ ПРИНЦИП (ЧИТАТЬ ПЕРВЫМ)

Это SaaS-платформа, а не просто CRM.

Tenant (Тенант) — это компания-клиент. У каждого тенанта своя физическая база данных (Database-per-Tenant, пакет stancl/tenancy).
Branch (Локация) — физический адрес/подразделение внутри тенанта, ГЛАВНАЯ операционная единица (см. п.4 — раньше называлась "Филиал", затем "Точка"; переименована в "Локация" — точнее отражает физическое местонахождение бизнеса — чтобы не путать с классическим "подразделение юрлица": здесь наоборот, юрлица подключаются к локации, а не локации к юрлицу). Код и идентификаторы (модель `Branch`, `branch_id`, роуты `*.branches.*`) намеренно не переименованы — это только смена русского термина в интерфейсе и документации. Один тенант может иметь много локаций.
Core (Ядро) — общий код платформы. Любая кастомизация тенанта (кастомные поля, формы) живет рядом с ядром в БД тенанта, а не меняет таблицы ядра.
Изоляция: Любая сущность, запрос, кеш-ключ или очередь обязаны быть в контексте конкретного тенанта. Забытый tenant-scope = утечка данных между компаниями. Это критический баг.
1. WORKFLOW АГЕНТА И ИНСТРУМЕНТЫ (TOOLS)

Твоя автономная работа строго регламентирована. Для задач, изменяющих код, правильная последовательность действий:

Read — прочитай существующий файл, если собираешься его менять.
Edit/Write — вноси изменения напрямую в рабочую копию (working tree). Edit — точечная правка (diff), Write — только для новых файлов или полной перезаписи. Отдельного шага "сохранить черновик" и ожидания применения патча человеком не существует — изменения сразу оказываются в файловой системе проекта.
Bash — используй для проверки (php -l, npx vite build, php artisan test), для git-операций и для любых shell-команд.
Git commit — НИКОГДА не коммить самостоятельно, если человек явно не попросил ("закоммить изменения" и т.п.). Внесённые правки остаются в рабочей копии как незакоммиченные изменения до отдельного явного запроса.
Ветки — не создавай feature-ветки автоматически; работай в той ветке, что уже активна, если человек явно не попросил создать новую.
Pull Request — создавай (gh pr create) ТОЛЬКО по явной просьбе человека, и только после того, как изменения закоммичены.
1.2. ФОРМАТТЕР PINT МОЛЧА УДАЛЯЕТ «НЕИСПОЛЬЗУЕМЫЕ» ИМПОРТЫ — ЛОВУШКА ПРИ ПРАВКЕ В НЕСКОЛЬКО ШАГОВ
После КАЖДОГО Edit/Write по .php-файлу автоматически прогоняется Pint (PostToolUse-хук). Он вырезает `use`-импорты, которые в этот момент нигде в файле не используются. Отсюда типичная ловушка: добавляешь `use App\Services\Foo;` одним Edit'ом, а первое обращение к `Foo::` собираешься дописать следующим — в промежуточном состоянии импорт выглядит неиспользуемым, и Pint его удаляет. Код после этого падает в рантайме с «Class App\Http\Middleware\Foo not found» (PHP резолвит короткое имя в текущий неймспейс), причём php -l такую ошибку НЕ ловит.
    * Правило: добавляй импорт и его ПЕРВОЕ использование ОДНИМ Edit'ом. Если это невозможно — сразу после серии правок проверь `grep -c 'ИмяКласса' файл.php` (импорт + все использования) и при необходимости верни `use` отдельным Edit'ом, когда использование уже в файле.
    * За одну эту сессию грабли сработали дважды (HandleInertiaRequests, routes/tenant.php) и оба раза находились только живым открытием страницы в браузере — 500-я ошибка. При правке роутов после такого фикса не забудь `php artisan route:clear && php artisan config:clear`.
    * Тот же форматтер однажды сломал расчёт ЗП, удалив импорт Client (см. §4, «Модуль ЗП покрыт тестами») — там это поймали тесты. Это не гипотетический риск.
1.1. ИЗВЕСТНЫЕ ОГРАНИЧЕНИЯ ЗАВИСИМОСТЕЙ
laravel/reverb ЖЁСТКО зафиксирован на 1.10.2 (не ^1.10.2) в composer.json — версия 1.11.0 регистрирует dev-команду прямо в ReverbServiceProvider::register() (Reverb::registerDevCommands()), а новый гвард Laravel 13.8 DevCommands::preventVendorRegistration() запрещает вендор-пакетам регистрировать dev-команды не из кода приложения — из-за этого ЛЮБОЙ php artisan (не только про Reverb) падает с "DevCommands should be registered in application code, not within vendor packages". Никогда не убирай точную версию на ^-диапазон и не обновляй laravel/reverb без проверки этого гварда.
2. КОМАНДЫ И ЗАПУСК (CLI)
Запуск проекта: php artisan serve (бэкенд) и npm run dev (фронтенд Vite). Домены маршрутизируются через dnsmasq (например, *.localhost).
Миграции ядра (Landlord DB): php artisan migrate
Миграции тенантов (Client DBs): php artisan tenants:migrate (применяет миграции из database/migrations/tenant ко всем базам).
Сидирование тенантов: php artisan tenants:seed
Тестирование (Tenant-aware): php artisan test --configuration=phpunit.tenant.xml — ЭТО ОСНОВНАЯ КОМАНДА ПРОВЕРКИ, гоняй её после любой правки бизнес-логики. Использует изолированную sandbox-БД тенанта tenant_agent_sandbox, каждый тест — в транзакции с откатом. Конфиг подключает ДВА каталога (<testsuite name="Agent"> — tests/Agent, <testsuite name="Unit"> — tests/Unit) — одной командой гоняются оба. tests/Feature пуст (только .gitkeep) — обычный `php artisan test` (central, phpunit.xml) теперь тоже полностью зелёный, но реального контента в нём нет, весь functional-тестинг живёт в tests/Agent.
    * Что реально покрыто (tests/Agent, ~25 тестов, требуют tenant-БД, прямой Eloquent/сервисы БЕЗ HTTP-стека): PayrollCalculationTest.php — расчёт ЗП (штатная бригада, доли, переопределения, подрядчики, изоляция ставок, самозанятые); WorkOrderVatCalculationTest.php — расчёт НДС на заказ-наряде в обоих режимах (inclusive/exclusive) и инвариант «без НДС суммы побайтово как раньше»; SandboxSmokeTest.php — базовая живость песочницы. ПРОГОНЯЙ ИХ при любой правке PayrollCalculationService, PayrollRule, связей исполнителей, recalculateTotals() и вообще всего, что влияет на суммы — это единственное место, где из данных заказа получаются реальные деньги людям. Новую логику расчёта покрывай тестом сразу, а не «потом».
    * tests/Unit (9 тестов, БД не требуют — extends голый PHPUnit\Framework\TestCase, не Laravel Tests\TestCase): DocumentRendererTest.php — рендер плейсхолдеров/условий/табличных секций документов. ОБЯЗАТЕЛЕН при любой правке DocumentRenderer/DocumentPlaceholderService.
    * tests/Agent/Auth + tests/Agent/ProfileTest.php + tests/Agent/WelcomePageTest.php (23+4 теста, РЕАЛЬНЫЙ HTTP-проход через маршруты) — закрывают пробел, который раньше маскировали central-тесты Breeze-скаффолда (tests/Feature/Auth/*, ProfileTest, ExampleTest — все УДАЛЕНЫ, не заводи их заново): те архитектурно не могли работать, т.к. /login, /register, /profile, '/' и т.п. в этом проекте существуют ТОЛЬКО внутри routes/tenant.php (require __DIR__.'/auth.php'), за middleware InitializeTenancyByDomain — то есть физически только на доменах тенантов, не на central-домене, по которому бил стандартный Laravel TestCase. Новые тесты бьют РЕАЛЬНЫМ HTTP-запросом (`$this->get($this->tenantUrl('/login'))` и т.п.) на домен sandbox-тенанта (`agent-sandbox.localhost`) — базовый класс `Tests\Agent\TenantHttpTestCase extends TenantAgentTestCase`.
        - ⚠️ TenantHttpTestCase снимает `App\Http\Middleware\PreventSandboxTenantHttpAccess` ТОЛЬКО для запросов внутри своего PHPUnit-процесса (`withoutMiddleware()`) — сама middleware не меняется и продолжает блокировать любой реальный HTTP-доступ (включая ручной curl с поддельным Host-заголовком) к sandbox-тенанту. Её собственный докблок прямо называет `phpunit.tenant.xml`-тесты штатным потребителем этого разрешения. НЕ путай это с ослаблением tenant-изоляции (§0/§8) — обычные Agent-тесты (без TenantHttpTestCase) этот обход не получают и не нуждаются в нём, т.к. не делают HTTP-запросов вообще.
        - Подписанные ссылки (verification.verify, middleware 'signed', НЕ 'signed:relative') требуют `URL::forceRootUrl($this->tenantUrl())` вокруг генерации — иначе подпись считается по central-домену (APP_URL) и не совпадёт при обращении по домену тенанта. Не забывай `forceRootUrl(null)` в finally — иначе подмена корня утечёт в следующий тест того же процесса.
    * ⚠️ ЖИВОЙ БАГ, НАЙДЕННЫЙ И ИСПРАВЛЕННЫЙ В TenantAgentTestCase (2027): откат транзакции годами НЕ РАБОТАЛ для tenant-БД. Причина — трейт `Illuminate\Foundation\Testing\DatabaseTransactions` открывает транзакцию автоматически изнутри `parent::setUp()`, т.е. ДО `tenancy()->initialize()`, когда `database.default` ещё central. Реальные записи (Payroll, WorkOrder и т.п.) уходили в tenant_agent_sandbox БЕЗ транзакции и коммитились НАВСЕГДА — при этом сами тесты оставались зелёными, баг был не виден по результату прогона. Обнаружено ТОЛЬКО эмпирически (создал пробную запись, тест прошёл, после завершения процесса запись осталась в БД) — чтение кода одно давало неверную уверенность. Текущая реализация открывает транзакцию вручную на связке `'tenant'` уже ПОСЛЕ `tenancy()->initialize()`. Если снова меняешь порядок setUp()/tearDown() в этом классе — обязательно перепроверяй эмпирически (создать запись → выйти из процесса → проверить БД), а не доверяй тому, что тесты прошли.
    * ПОСЛЕДСТВИЕ этого бага (устранено 2027, для истории — почему цифры в sandbox когда-то были огромными): из-за многолетней неработающей транзакции в tenant_agent_sandbox накопился мусор от PayrollCalculationTest/WorkOrderVatCalculationTest в промышленных масштабах (1440 Branch «Тестовая локация НДС», 2271 Client, 1480 WorkOrder и т.д.) — тесты создавали фикстуры в setUp() на каждый прогон, откат не срабатывал, и они оставались навечно. Вычищено вручную (TRUNCATE по бизнес-таблицам, кроме легитимного seed-набора — accounts/lookups/modules/permissions/pipelines/pipeline_stages/settings/migrations). Если снова увидишь в tenant_agent_sandbox тысячи однотипных записей — это либо рецидив этого бага, либо кто-то создаёт фикстуры вне транзакции; НЕ списывай это на «наверное, так и должно быть», это всегда симптом.
    * 🚫 ПРАВИЛО: любой тест обязан ПОЛНОСТЬЮ убирать за собой созданные им данные — не только в central, но и в tenant-БД (реальная персистентная MySQL, не sqlite :memory:, которую можно просто выбросить). Это не «хорошо бы», а обязательное условие: sandbox — общий на все прогоны ресурс, и любая утечка одного теста тихо портит результаты всех последующих (например, "проверка, что список пуст" начинает падать не из-за реального бага, а из-за мусора от другого теста). Если тест пишет в tenant-БД мимо стандартного отката `TenantAgentTestCase` (например, напрямую через `DB::` на другой связке, через очередь/джобу, которая коммитит сама, или через внешний процесс) — откат за него не отвечает, значит подчистка делается вручную в `tearDown()`. Раньше в этом проекте уже была уверенность, что "откат подчищает всё" — она оказалась неверной (см. пункт выше) и обнаружилась только через реальный разросшийся мусор в БД, а не через код-ревью. Поэтому: при любом подозрении, что тестовые данные могли остаться — проверяй ЭМПИРИЧЕСКИ (посчитай строки в затронутых таблицах до и после прогона), не доверяй одному факту "тест прошёл, значит и откатился".
Миграции тенантов на песочнице: php artisan tenants:migrate --tenants=tenant_agent_sandbox --path=database/migrations/tenant --force — так новая миграция проверяется до применения на остальных тенантах. Миграцию, которая переносит данные, ОБЯЗАТЕЛЬНО прогони на подсаженных тестовых записях (транзакция + rollback), а не только на пустой базе: код, который «ничего не ломает при отсутствии данных», ошибку покажет позже и дороже.
Тесты (PHPUnit 12): Используй атрибут #[Test] из PHPUnit\Framework\Attributes\Test или префикс test в названии метода. Doc-comment @test больше не поддерживается.

4. БИЗНЕС-ЛОГИКА И СУЩНОСТИ
Локация (Branch) vs Юрлицо (Legal Entity) — многие-ко-многим (с 2027_01_28, переименовано из "Филиал"):
    * Локация — главная операционная единица, физический адрес/подразделение: Сотрудники, Расписание, Склады, Заказы, Клиенты — всё висит на ней. Обязательна всегда (branch_id — не изменилось). Одной локации достаточно для работы вообще без единого юрлица (документы просто будут без реквизитов, никакой ошибки).
    * Юрлицо — исключительно финансовый профиль (Кассы, Реквизиты, подписанты для документов). Юрлицо не бывает "само по себе" — обязательно привязано хотя бы к одной локации (кроме самой первой локации в системе, которая создаётся автоматически — см. ниже), но привязка настраивается СО СТОРОНЫ юрлица (Settings/LegalEntities — мультивыбор локаций), не со стороны локации.
    * Связь `branch_legal_entity` (пивот, без дополнительных колонок) — заменила старую единственную колонку `branches.legal_entity_id` (1:0..1). Причина: одна локация нередко реально выставляет документы от нескольких юрлиц одновременно (например, часть заказов — от ИП, часть — от ООО), а старая схема такое не могла выразить без завода "локаций-дублей". `Branch::legalEntities()` / `LegalEntity::branches()` — обе BelongsToMany.
    * Раз у локации может быть несколько юрлиц, "какое юрлицо у ЭТОГО конкретного заказа" больше не выводится однозначно через branch — у WorkOrder есть собственное nullable `legal_entity_id` (тот же паттерн распространяется на любую новую запись, которой нужен явный выбор юрлица — в Фазе 17 его получает Deal; для Client/Transaction пока не заводили за отсутствием потребности). `DocumentPlaceholderService::resolveLegalEntity()`: приоритет — явный `$entity->legal_entity_id`; иначе — юрлицо локации, ТОЛЬКО если оно у неё ровно одно (иначе неоднозначно); если и так не определить — null, документ формируется с пустыми реквизитами (`DocumentGenerationService` не бросает исключение — локация/заказ имеют право работать без юрлица). Нумерация документа без юрлица — не через DocumentNumerator (тот атомарно скопирован именно на legal_entity_id, NOT NULL FK), а через сентинел-схему `БН-<дата>-<рандом>` — такой документ не претендует на бухгалтерскую сплошную нумерацию.
    * WorkOrderController::store()/update() валидируют legal_entity_id серверно (не только фронтом): выбранное юрлицо обязано реально входить в branch->legalEntities() этой локации — иначе ValidationException.
    * Автобутстрап: LegalEntityController::store() при Branch::count() === 0 (не "это первое юрлицо", а именно "локаций в системе вообще нет" — так срабатывает и для тенанта, который все локации удалил) сам создаёт локацию «Основная» и сразу привязывает к ней новое юрлицо — без этого первое же создание заказа у только что зарегистрированного тенанта (RegisterTenantController локацию не создаёт) упёрлось бы в пустой список локаций.
    * Сайдбар (AppHeader.vue): переключатель юрлица (если их >1) и локации (если доступно локаций >1 после фильтра по выбранному юрлицу, включая локации без единого юрлица) — независимые кнопки. LegalEntityController::switch() сбрасывает выбранную локацию на "Все" ТОЛЬКО если она не входит в новое юрлицо (а не всегда, как было раньше) — локация с несколькими юрлицами не заставляет пользователя перевыбирать её при каждом переключении юрлица. BranchController::switch() автоследует в юрлицо локации, только если оно у неё РОВНО одно (иначе никакого умолчания, выбор явно за пользователем).

Правило то же, что и у сверки/закрытия периода (§8, "Право администратора на удаление без ограничений" сюда НЕ применяется — это защита целостности данных, не workflow-статус, обхода для admin нет нигде из перечисленного):

Баннер на странице настроек — не блокирующий, только информирует.

Смена `owner_type`/`owner_id` у активного склада (перенос в другое место) НЕ проверяется — осознанная граница, редкое действие, не «тихая потеря покрытия».

Тот же принцип "автобутстрап инфраструктуры вместо невозможного состояния", что и у `LegalEntityController::store()` (автосоздание локации «Основная», см. выше).

Per-line override остаётся: `updateItemMaterialSettings()` принимает `allow_negative_stock` для ЛЮБОЙ позиции-товара (гейт по `itemable_type === Product::class`, не по `isMaterial()`), а материал-специфичные поля (`is_billable`/`affects_payroll`/`payroll_uses_cost_only`/`stock_deduction_disabled`) — ТОЛЬКО когда `isMaterial()` — сервер молча не принимает их для обычного товара (не в списке правил валидации), а не отклоняет весь запрос: иначе случайный лишний параметр во фронтовом запросе не должен ломать сохранение единственного релевантного тумблера. `WorkOrderItemMaterialSettingsModal.vue` показывает материалу все 5 тумблеров, обычному товару — только «Разрешить списание в минус» (заголовок модалки тоже меняется: «Настройки материала» / «Настройки списания»), иконка настроек в дровере видна для товара только при включённом складе (иначе там нечего показывать).
        - Настройки материала — иконка (аналог `ri-team-line` у услуг) рядом с материалом в дровере корзины, открывает `WorkOrderItemMaterialSettingsModal.vue` (выделенный эндпоинт `PUT .../items/{item}/material-settings`, калька структуры с `WorkOrderItemPayoutModal.vue`, через `<Modal>`): 5 тумблеров + справочный блок себестоимость/наценка-в-деньгах/наценка-в-% (показывается, только если цена материала выставлена выше себестоимости).
        - Автодобавление — `ServiceDefaultMaterial` (service_id, product_id, quantity; CRUD в Settings → Услуги, `ServiceController::store/update/destroyDefaultMaterial`) описывает «эта услуга обычно тратит этот материал в этом количестве». Тенантский `Setting.service_material_auto_add_mode` (`off`/`confirm`/`silent`, default `confirm`, Настройки → Склад) управляет поведением при добавлении услуги в заказ: `off` — ничего; `confirm` — модалка `ServiceMaterialAutoAddModal.vue` со списком материалов на подтверждение; `silent` — материалы добавляются сразу без диалога. Триггер (`maybeTriggerMaterialAutoAdd()`) вызывается из ОБОИХ мест, где услуга реально добавляется в заказ (`addItemDirect()` и `submitItem()` в `Operations/WorkOrders/Show.vue`) — та же ловушка «два места», что уже документирована выше у подстановки цены товара. Контроль остатков — `WorkOrderController::autoAddMaterials()`: при включённом складе и нехватке остатка без `force_negative` материал НЕ добавляется, а пропуск логируется в «Историю» заказа (`ActivityLogger`) человекочитаемым текстом — во фронтенде проекта нет рабочего toast-механизма (`flash.warning` нигде не читается), поэтому для тихого уведомления используется уже существующая и всегда видимая вкладка «История», а не новая инфраструктура.
        - Материалы визуально гнездятся под своей услугой в дровере/таблице заказа (отступ, приглушённый стиль, бейдж «Материал», суффикс «· скрыт» при `is_billable=false`) — не показываются вперемешку с обычными позициями.
        - Реверса склада/ЗП при уходе статуса заказа с `completed` не существует нигде в системе (см. `updateStatus()`) — материалы наследуют это же поведение симметрично, это не регресс данной фичи, а существующая граница.
        - Известный осознанный компромисс: если менеджер вручную поставит цену материала НИЖЕ себестоимости (материал «в подарок»), `payroll_uses_cost_only` не показывается (условие `price > cost_price` не выполняется) — вычет из ЗП пойдёт по заниженной цене, не по реальной себестоимости. Не усложняем формулу ради этого краевого случая без отдельного запроса.
        - Фильтр каталога по остаткам (реализовано) — при включённом складе каталоги, из которых добавляют товар/материал в заказ (вкладка «Товары» в дровере, `AddMaterialModal.vue`, `<select>` в модалке «Быстрый поиск»), показывают ТОЛЬКО позиции с суммарным остатком `> 0` хотя бы на одном складе — карточка товара без единой поставки не предлагается к добавлению. `WorkOrderController::show()` подмешивает `stockBalances:id,product_id,warehouse_id,quantity` в `products` (только при `WarehouseResolver::isEnabled()`) и передаёт список складов отдельным пропом `warehouses`. Фильтрация — на фронте, суммированием `stock_balances` по товару (`productStockQuantity()`), не отдельным запросом на каждое открытие каталога.
        - Список складов для фильтра — `WarehouseResolver::candidateWarehousesFor(Branch $branch)`, НЕ «все активные склады тенанта»: он обязан предлагать ровно тот выбор, который реально на что-то влияет в `resolveFor()` для ЭТОЙ локации в текущем `warehouse_mode`, иначе фильтр выглядел бы рабочим, но был бы обманчив. `shared` — список ВСЕГДА пуст (списание идёт с одного и того же дефолтного склада компании независимо от того, сколько складов в системе, — выбор ничего не меняет, `<select>` в UI не показывается вовсе, `warehouses.length > 1` и так это гарантирует). `mixed` — общие (`owner_type=company`) склады + склады ЭТОЙ локации (через `branch_warehouse`, фолбэк на `owner_type=branch`/`owner_id=branch.id` — тот же порядок, что в `resolveFor()`), БЕЗ складов других локаций. `per_branch` — только склады этой локации, тем же порядком pivot→фолбэк. Фронту отдельно ничего не считать не нужно — `<select>` в дровере (`catalogWarehouseFilter`) и в `AddMaterialModal.vue` (`selectedWarehouseId`) уже были написаны на условии «показать, если `warehouses.length > 1`» ДО того, как список стал режимо-зависимым — сама коррекция потребовала правки только бэкенда, фронт не тронут. Покрыто `tests/Agent/WarehouseResolverCandidatesTest.php` (5 тестов на все три режима + фолбэк без pivot + исключение неактивных складов).

НДС (Фаза "Поддержка НДС") — реализовано: настройка живёт НА УРОВНЕ ЮРЛИЦА (`LegalEntity.vat_payer`/`vat_rate`/`vat_calculation_method`), НЕ глобально на тенанта — у одного тенанта могут одновременно быть юрлица с разными налоговыми режимами (например ИП на патенте без НДС и ООО на ОСН с НДС). Список допустимых ставок по стране — `CountryConfigService` (новый блок `vat` в конфиге каждой страны: `applicable`/`rates`/`default_rate`/`label`), тот же принцип "один источник истины", что и у `requisite_schema`; добавление ставки/страны — правка только этого сервиса. `LegalEntityController::store()/update()` валидируют `vat_rate` строго по списку страны и обнуляют оба НДС-поля, если `vat_payer=false` (см. `validateVatFields()`). UI — отдельная вкладка «НДС» в форме юрлица (`Settings/LegalEntities/Index.vue`), не часть `requisite_schema`/`signatory_schema` — это про расчёт денег, а не про реквизиты/подписантов, и поля (чекбокс+select) не укладываются в текущий text/textarea-рендерер схемы.
   * Формула расчёта — `vat_calculation_method`: `inclusive` (цена уже включает НДС — налог просто выделяется отдельной строкой, итоговая сумма к оплате НЕ меняется) или `exclusive` (НДС начисляется сверх уже посчитанной суммы позиций — итог увеличивается). КЛЮЧЕВОЙ инвариант всей реализации: когда юрлицо записи не резолвится или `vat_payer=false`, формулы `total_amount`/`discount_amount`/`final_amount` (`WorkOrder`) и `total_value` (`GoodsReceipt`) остаются ПОБАЙТОВО идентичны версии до появления НДС в системе — это единственная гарантия того, что существующие тенанты без НДС не увидели ни одного изменения в суммах/оплатах/ЗП. Слой оплат (`FinanceService`, `processPayment`, `syncPaymentStatus`) НДС вообще не касается — `final_amount`/`total_value` по построению всегда остаются "суммой к оплате" в обоих режимах, платежи сверяются с ними как раньше.
   * Резолюция юрлица для расчёта НДС — ТОТ ЖЕ метод, что и у печатных документов (`DocumentPlaceholderService::resolveLegalEntity()`, публичный статический), переиспользуется из `WorkOrderController::recalculateTotals()` и `StockService::resolveVatConfig()` — иначе расчёт НДС и то, что показывает документ, могли бы разойтись.
   * Ставка/сумма НДС СНЕПШОТЯТСЯ на самой записи в момент пересчёта позиций (`work_orders.vat_rate`/`vat_amount`, `goods_receipt_items.vat_rate`/`vat_amount` — на заказе ставка ОДНА на весь документ, на накладной — ПО КАЖДОЙ позиции отдельно, т.к. у одного поставщика товары технически бывают на разных ставках), а НЕ читаются заново из юрлица при каждом открытии — тот же принцип, что и у `Document::isStale()` ("зафиксированный во времени артефакт"): если юрлицо потом сменит ставку, уже посчитанные заказы/накладные не пересчитываются молча. Пересчёт происходит при каждом изменении состава позиций (как и раньше — `recalculateTotals()` уже вызывался на каждый `addItem`/`updateItem`/`removeItem`/`updateDiscount`), не только один раз при создании.
   * Ставка НДС `0` — ВАЛИДНЫЙ режим (экспорт/льгота), а НЕ "НДС выключен" — UI и плейсхолдеры документов проверяют именно `vat_rate !== null`, а не truthy-проверку значения.
   * Плейсхолдеры документов — аддитивные ключи `work_order.vat_rate`/`vat_amount`/`total_amount_without_vat` и `goods_receipt.vat_amount`/`total_value_without_vat` + `item.vat_rate`/`vat_amount` в табличной секции накладной (`DocumentPlaceholderService`, `DocumentTemplateController::ENTITY_PLACEHOLDERS`/`ENTITY_TABLE_PLACEHOLDERS`) — пустая строка, если НДС не применялся; `DocumentRenderer` их автоматически вырезает, старые шаблоны рендерятся без единого изменения.
   * Себестоимость на складе (`StockBalance.avg_cost`, `ProductBatch.cost_price`) считается от `cost_price` "как есть", БЕЗ вычета входящего НДС — сознательная граница объёма (полноценный учёт возмещаемого НДС/маржи нетто — отдельная кратно более крупная задача, не входила в эту фазу).
Скидки на заказ-наряде — ДВА ВЗАИМОИСКЛЮЧАЮЩИХ механизма (реализовано):
    * Скидка на заказ целиком — `WorkOrder.discount_amount` + `discount_is_manual` (авторасчёт по грейду клиента, пока флаг false — см. Фазу 14.4). Скидка на отдельную позицию — `WorkOrderItem.discount_amount`, она вычитается прямо в `WorkOrderItem.total` при записи (`total = qty × price − discount_amount`).
    * ЖЕЛЕЗНОЕ ПРАВИЛО: одновременно применять оба нельзя — иначе сумма к оплате считалась бы с двойной скидкой, а пользователю было бы не очевидно, откуда она взялась. Проверка живёт СЕРВЕРНО в трёх методах `WorkOrderController`: `updateDiscount()` (отказ, если хоть у одной позиции `discount_amount > 0`), `addItem()` и `updateItem()` (отказ, если на заказе уже задана ручная общая скидка). UI дублирует это блокировкой полей с пояснением причины (правило §6 «Объяснение блокировок в UI»): в дровере корзины, в модалке «Скидка на заказ» и в инлайн-поле скидки позиции. Не «упрощай» это до одной лишь фронтовой блокировки.
    * Авто-скидка по грейду клиента (`discount_is_manual = false`) под это правило НЕ подпадает — она сосуществует со скидками по позициям как и раньше. Взаимоисключение касается именно РУЧНОЙ общей скидки. Это осознанная граница, а не недосмотр.
    * Отображение: сумма скидок по позициям (`Σ item.discount_amount`) обязана показываться отдельной строкой «Скидка по позициям» во ВСЕХ трёх местах сводки в `Operations/WorkOrders/Show.vue` (блок «Итоги» под таблицей, сайдбар «Финансы», подвал дровера корзины). До этой правки позиционная скидка была молча спрятана внутри `total_amount` и нигде не показывалась — заказ выглядел так, будто скидки нет вовсе.
    * ⚠️ ПЛЕЙСХОЛДЕРЫ ДОКУМЕНТОВ И ЭТА СКИДКА. `WorkOrder.total_amount` (колонка БД) уже НЕТТО по позиционным скидкам. Поэтому `DocumentPlaceholderService::workOrderPlaceholders()` СОЗНАТЕЛЬНО не отдаёт колонку как есть, а считает заново: `work_order.total_amount`/`items_total` — ВАЛОВАЯ сумма `Σ(qty × price)` до любых скидок, `work_order.discount_amount` — СУММАРНАЯ скидка (общая + по позициям). Иначе в печатной форме «Сумма позиций − Скидка» переставало сходиться с «Итого». Ключи плейсхолдеров при этом НЕ менялись — уже созданные тенантами шаблоны продолжают работать без правок. Дополнительно есть опциональный флаг-условие `item.has_discount` для табличной секции (по образцу `item.has_vat`).
Универсальные справочники (Lookups):
    * Простые списки (источники клиентов, типы кузова) хранятся в единой таблице lookups. На фронте используется компонент <CreatableSelect> для добавления на лету.
    * Lookup.is_system=true — защищённая запись: LookupController::update()/destroy() отказываются её менять и удалять. Так помечены 3 базовые роли клиента (см. следующий пункт) — заводить поверх них свои значения пользователь по-прежнему может.
Роли клиента (client_roles) — многие-ко-многим, НЕ строковая колонка:
    * У клиента может быть сразу несколько ролей одновременно (например, и Подрядчик, и Поставщик) — пивот `client_roles` на Lookup(type=client_role), связь Client::roles(). Колонки clients.role больше НЕТ (миграция 2027_01_30 перенесла данные и удалила её) — если встретишь $client->role, это устаревший код.
    * 3 системные роли заводятся той же миграцией и защищены is_system: «Клиент», «Подрядчик», «Поставщик». Роль «Подрядчик» — не просто метка: именно она даёт клиенту право быть исполнителем услуги (см. п.4, Подрядчики) и иметь собственную ставку ЗП. Её значение захардкожено константой CONTRACTOR_ROLE в WorkOrderController/PayrollSettingsController — при переименовании роли в справочнике связь порвётся, поэтому она и системная.
    * Системные роли клиента, как и любая is_system-запись, НЕЛЬЗЯ ни удалить, ни переименовать — даже пользователю с ролью admin (LookupController::update()/destroy() блокируют is_system целиком, без исключений; см. §8 «Право администратора на удаление без ограничений»: системные справочники прямо перечислены как то, что этим правилом НЕ покрывается). Переименование окончательно и сознательно НЕ реализовано, хотя технически возможно: решили, что риск случайной правки текста роли важнее удобства — это не пробел в реализации, а закрытый вопрос, не заводи задачу на него без нового прямого запроса владельца. `value`/`label` тем не менее уже разведены по образцу work_order_status ('client'/'contractor'/'supplier' — стабильный слаг в value, русский текст в label, миграция 2027_02_02); сейчас label просто более читаемое имя колонки для отображения, редактировать его неоткуда. CONTRACTOR_ROLE в WorkOrderController/PayrollSettingsController — value-слаг 'contractor' (константа CONTRACTOR_ROLE_LABEL = 'Подрядчик' — для текста ошибок, захардкожена, а не читается из БД, потому что раз переименование запрещено, она гарантированно не разъедется с label).
    * Фильтр по роли в списке клиентов делается через whereHas, а НЕ через QueryFilterService (тот работает по колонкам таблицы, а колонки role больше нет) — см. ClientController::index(), там же обрабатывается отдельно и фильтр по RFM-сегменту.
Финансы (Accounts / Transactions):
    * Счета (Account) бывают 4 типов: cash (касса), bank (расчетный счет), acquiring (эквайринг, имеет commission_percent), bonus (единственный системный виртуальный счет тенанта для оплаты бонусами клиента — не привязан к юрлицу, не редактируется через обычную форму счетов).
    * Любое изменение Account.balance — ТОЛЬКО через FinanceService (processTransaction/processTransfer/updateTransaction/revertTransaction). Никогда не трогай balance напрямую в контроллере.
    * У Transaction есть transaction_date (бизнес-дата операции, редактируется, можно вносить задним числом) отдельно от created_at (техническая метка создания записи, никогда не меняется).
    * Редактирование транзакции — O(1) пересчет баланса счета дельтой (новая сумма минус старая), а не полный пересчет по истории.
    * Сверка (is_reconciled) блокирует правку суммы/даты, пока не снята. Закрытие периода (finance_period_closures, PeriodClosureService::assertNotClosed) блокирует создание/правку/отмену операций с датой не позже границы закрытия — обе проверки живут внутри FinanceService, не дублируй их в контроллерах.
    * Дневные снэпшоты остатков (account_daily_snapshots, AccountSnapshotService) считаются независимо по каждой дате (не цепочкой от предыдущего дня).
    * Автоподстановка банка по БИК — App\Services\DadataService::lookupBank() (DaData Suggestions API, findById/bank), вызывается из AccountController::lookupBik() (GET /settings/accounts/bik-lookup). Токен — тот же паттерн, что wappi_master_token (Фаза 16): App\Models\Central\PlatformSetting (central БД, ключ dadata_api_key, вносится администратором платформы в /admin/settings), читается из тенантского кода ТОЛЬКО через tenancy()->central(...) — тенант сам ключ не вводит и не видит. Settings/LegalEntities/Index.vue держит bank_name/corr_account нередактируемыми (readonly), пока DaData настроена и БИК валиден — защита от рассинхрона названия банка и БИК в документах; ЕСЛИ ключ не настроен (DadataService::isConfigured()===false) — фолбэк на ручной ввод с явным предупреждением (не блокируй создание счетов из-за неподключённой сторонней интеграции). Банк с state.status!=='ACTIVE' (отозванная лицензия) DaData всё равно возвращает в suggestions — lookupBank() отфильтровывает такие результаты как null.
Исполнители позиции заказа и Подрядчики (полиморфная связь):
    * Исполнителем позиции-услуги может быть штатный сотрудник (Employee) ИЛИ подрядчик (Client с ролью «Подрядчик»). Обе стороны живут в одной полиморфной таблице `work_order_item_assignees` (assignee_type/assignee_id — тот же приём, что у work_order_items.itemable). Связи: WorkOrderItem::employees() и WorkOrderItem::contractors(), обе BelongsToMany через withPivotValue('assignee_type', ...) — она и фильтрует выборку, и проставляет тип при attach()/sync(), поэтому каждая связь видит и синхронизирует ТОЛЬКО свои строки. Таблицы work_order_item_employees больше нет (миграция 2027_01_31_000000).
    * ЖЕЛЕЗНОЕ ПРАВИЛО: на одной позиции нельзя одновременно держать штатных исполнителей и подрядчиков. Причина не формальная: у них принципиально разные схемы расчёта (бригада делит базу долями, подрядчик получает свою сумму целиком), и смесь не имеет понятного смысла. На уровне схемы это НЕ выражается (обе стороны — строки одной таблицы), поэтому проверка живёт в WorkOrderController::assigneeTypesMixedError() плюс дублируется в UI (AssigneeMultiSelect блокирует второй режим). Сам расчёт намеренно НЕ полагается на инвариант и корректно обработает обе коллекции, если его когда-то нарушат в обход контроллера.
    * Администратор позиции — ВСЕГДА штатный сотрудник (work_order_admins / work_order_item_admins не полиморфны). Позиция с подрядчиком-исполнителем при этом может иметь администратора — это разрешено и нормально.
    * Employee.type='outsource' УПРАЗДНЁН (миграция 2027_02_01 перевела таких сотрудников в клиентов-подрядчиков). Остались только 'staff' и 'self_employed'. Не возвращай этот тип: подрядчик должен существовать ровно в одном виде, иначе непонятно, где его заводить и почему у одних есть карточка клиента с реквизитами, а у других — карточка сотрудника с датой найма.
    * Подрядчика можно поставить в календарь — реализовано: Appointment.contractor_id (nullable FK на clients, nullOnDelete) — альтернатива employee_id, заполнен максимум один из двух. Сознательно НЕ полиморфная пара assignee_type/assignee_id без FK (как у work_order_item_assignees — то оправдано КОЛЛЕКЦИЕЙ из многих исполнителей на позицию); у Appointment исполнитель ровно один, поэтому применён тот же паттерн, что уже есть у payrolls.employee_id/client_id (Payroll::payee()) — пара настоящих FK строго лучше там, где не нужна гибкость полиморфизма. Appointment::assignee()/assigneeName() резолвят исполнителя независимо от того, в какой из двух колонок он записан. Инвариант "не оба сразу" — AppointmentController::validateAppointment() (contractorRoleRule() — исполнителем-подрядчиком можно назначить только Client с ролью «Подрядчик», тот же принцип, что WorkOrderController::assertAssigneeIdsExist()). AppointmentController::convertToWorkOrder() при конвертации ветвится на WorkOrderItem::employees()->sync()/contractors()->sync() по тому, что заполнено. UI — Operations/Appointments/Index.vue: простой toggle "Сотрудник/Подрядчик" (НЕ AssigneeMultiSelect — тот для коллекции многих исполнителей, здесь ровно один). Drag-reschedule (rescheduleAppointment()) и calendarEvents() ОБЯЗАНЫ пробрасывать contractor_id наравне с employee_id — забытое поле в PUT-payload молча стирает назначенного подрядчика при любом перетаскивании записи мышью.
Расчёт ЗП (PayrollCalculationService) — отличия подрядчика от штатного исполнителя:
    * Подрядчик ВНЕ пула долей: получает свою сумму целиком, share_percent к нему не применяется. Штатные исполнители, наоборот, делят базу между собой все без исключения (типов, выпадающих из знаменателя, больше нет).
    * У подрядчика НЕТ должности, поэтому каскад ставки для него короче: только его персональные правила (payroll_rules.client_id) — ступени «ставка должности» не существует в принципе. Общей ставки «на всех подрядчиков сразу» тоже нет.
    * Компенсация налога самозанятого к подрядчику НЕ применяется — он выставляет свою цену сам, гросс-ап был бы двойным начислением.
    * PayrollRule адресуется ровно одному из трёх: position_id | employee_id | client_id. Кандидаты поиска ставки обязаны задавать ВСЕ колонки из RULE_TARGET_COLUMNS (незаданные = NULL) — иначе недостающая колонка не попадёт в WHERE, и ставка сотрудника случайно подберёт правило подрядчика (человек получит чужие деньги). Для этого есть хелпер ruleCandidate().
    * payrolls: employee_id и client_id оба nullable, заполнен ровно один. CHECK-констрейнта нет намеренно (MySQL 5.7 молча его игнорирует) — инвариант держат PayrollCalculationService и PayrollController. Для «кому начислено» есть Payroll::payee()/payeeName(), не ветвись руками.
    * Модуль ЗП ПОКРЫТ ТЕСТАМИ — tests/Agent/PayrollCalculationTest.php (запуск: php artisan test --configuration=phpunit.tenant.xml). Это единственное место, где из данных заказа получаются реальные деньги людям, поэтому при любой правке расчёта тесты обязательны к прогону, а новые сценарии — к добавлению. Тесты уже ловили реальный баг (форматтер удалил импорт Client, и тип резолвился в несуществующий App\Services\Client).

Токен — App\Models\Central\PlatformSetting (central БД, ключ wappi_master_token), вносится администратором платформы в /admin/settings (Фаза 16), читается из tenant-контекста ТОЛЬКО через tenancy()->central(fn () => PlatformSetting::get(...)) — прямой Eloquent-запрос из тенантского кода попадёт не в ту БД. Профиль в Wappi при подключении канала создаёт сама система — WappiProProvider::provisionProfile() именует его "{tenant_id}-{channel_id}" (домен тенанта + id локальной записи, а не номер телефона — тот физически не известен до сканирования QR) и сначала проверяет список существующих профилей по имени (защита от дублей при ретрае после сбоя), только потом создаёт новый. При удалении канала — releaseProfile() (best-effort), чтобы отключённые номера не копились в общем аккаунте.

Один и тот же фронтенд-компонент (ChatPanel.vue) годится под оба случая. Chat НЕ имеет глобального BranchScope (внутренние чаты не должны пропадать при выбранной локации, где branch_id всегда null) — фильтрация по локации для внешних чатов делается явно в контроллере.

POST /broadcasting/auth и Broadcast::channel()-коллбэки (routes/channels.php) подключены вручную ВНУТРИ routes/tenant.php (Route::middleware('auth')->group(...)), а НЕ через withRouting(channels: ...) в bootstrap/app.php — иначе авторизация канала выполнялась бы без InitializeTenancyByDomain и стучалась бы в central БД, где нет chats/messages. 5. КАСТОМИЗАЦИЯ (EAV) И ПРАВА (ABAC)
Гибридный EAV: Системные поля фиксированы в таблицах. Кастомные поля хранятся в custom_field_definitions и custom_field_values. Для фильтрации значения дублируются в типизированные колонки (value_text, value_number, value_date).
    * Кастомное поле в шаблонах документов и сообщений (реализовано, миграция 2027_02_12): тумблер `CustomFieldDefinition.use_in_templates` делает поле доступным как плейсхолдер `{{<entity_type>.custom.<key>}}`. Единый источник значений для ОБОИХ потребителей — `App\Services\CustomFieldPlaceholderService` (`forEntity()` — значения конкретной записи, `hintsFor()` — подсказки для пикера); он один намеренно, чтобы формат значения (дата d.m.Y, чекбокс Да/Нет, число без хвостовых нулей) не разъехался между печатной формой и текстом сообщения.
    * Подключено в `DocumentPlaceholderService::buildFor()` (для work_order дополнительно подмешиваются кастомные поля вложенных client и vehicle — их обычные плейсхолдеры вида client.name/vehicle.plate_number там уже есть) и в `MessageTemplateService` (клиент — в обоих триггерах, заказ-наряд — в work_order.ready). Реестры подсказок собираются ДИНАМИЧЕСКИ: `DocumentTemplateController::entityPlaceholdersWithCustomFields()` и `MessageTemplateController::STATIC_PLACEHOLDERS` + `TRIGGER_CUSTOM_FIELD_ENTITIES`. Заводя новую сущность с кастомными полями, не забудь про оба реестра.
    * ⚠️ entity_type кастомных полей ('client','vehicle','work_order','employee' — список зашит в валидацию `CustomFieldController::store()` И в объект `entityTypes` во фронте `Settings/CustomFields/Index.vue`, эти два места обязаны совпадать) НЕ СОВПАДАЕТ с реестром сущностей документов `DocumentTemplateController::ENTITY_TYPES` ('work_order','transaction','client','goods_receipt'). Пересечение — только work_order и client. Для vehicle/employee плейсхолдер технически заведётся, но подставлять его пока некуда — UI об этом честно предупреждает, и это не баг.
Динамические списки: Все таблицы (Index) строятся динамически на базе list_views (настройки колонок пользователя) и фильтруются через FieldPermissionService.
Гранулярные права (ABAC):
    * Доступ к данным (Scopes: Локации, Юрлица, Склады) вычисляется один раз при логине и кэшируется через UserScopeCachingService.
    * Приоритет прав: Индивидуальные права Пользователя (user_branches) перекрывают права Роли (role_branches).
6. КОНВЕНЦИИ И ПРАВИЛА НАПИСАНИЯ КОДА
Валидация: Всегда используй строгую валидацию ($request->validate() или Form Requests). Никогда не доверяй $request->all().
Деньги: Все денежные суммы в БД хранятся ТОЛЬКО в integer (в копейках/центах). Использование float запрещено.
Мультиязычность (Natural Language Keys) — ⚠️ МИНИМАЛЬНАЯ ОБВЯЗКА ПОДКЛЮЧЕНА (Фаза O, перед Фазой 17 этапом 2), но перевода как такового ЕЩЁ НЕТ — пиши обычный русский текст, как раньше. Что сделано: `resources/js/app.js` инициализирует `createI18n({ legacy: false, globalInjection: true, locale: 'ru', fallbackLocale: 'ru', messages: { ru: {} }, missingWarn: false, fallbackWarn: false })`, подключён через `.use(i18n)` — значит `$t('Любой текст')` теперь не падает в рантайме нигде во Vue (вернёт сам переданный ключ как есть, т.к. словарь `ru` пуст и warn отключены). `vite.config.js`: `optimizeDeps: { exclude: ['vue-i18n'] }` — обязательно, БЕЗ этого сборка падает с `ReferenceError: init_runtime_dom_esm_bundler is not defined` (Rolldown-Vite 8 несовместим с ESM-пребандлом vue-i18n@11 через обычный optimizeDeps, это не проблема кеша — воспроизводится и на чистом `node_modules/.vite`). Существующие ~100 файлов интерфейса как писали русский текст литералами, так и продолжают — это НЕ откат правила, просто массовое оборачивание в $t() по всему фронту само по себе не входило в эту фазу и остаётся отдельной задачей по явному запросу владельца (когда реально понадобится вторая локаль). Новый код тоже пиши обычным текстом, НЕ начинай выборочно оборачивать — единообразие важнее. Модели через spatie/laravel-translatable — это ДРУГОЙ, живой и работающий механизм (см. следующий пункт), его не путать с фронтовым i18n.
Переводимые модели: Из-за пакета spatie/laravel-translatable прямое обращение $model->name возвращает строку. При обновлении всегда используй $model->getTranslations('name'), иначе получишь ошибку Cannot access offset of type string on string.
Серверная пагинация: Запрещено использовать ->get() для списков. Всегда используй ->paginate(15)->withQueryString() + QueryFilterService::apply().
Асинхронность: Любой экспорт (bulkExport), массовое удаление или тяжелые операции обязаны выполняться через Laravel Horizon (Jobs).
Часовые пояса: Сервер работает в UTC. Календарный день клиента определяется часовым поясом локации (Branch::timezone) с фолбэком на пояс тенанта (Tenant::timezone, обязателен при регистрации). Любая бизнес-логика, зависящая от "какой сейчас день" (дефолтные даты операций, ночные джобы, отчеты "за сегодня/вчера", закрытие периода) — ОБЯЗАНА идти через TimezoneResolver::forBranch()/forTenant(), а не через голый now()/Carbon::today() (= UTC, не время клиента). Cron-задача, зависящая от календарного дня клиента, не может быть одним dailyAt() — см. TakeDailyAccountSnapshots (ежечасная проверка "не наступила ли полночь" по каждому используемому часовому поясу). Исключение — метки аудита (created_at, edited_at, reconciled_at и т.п.): они остаются в UTC, в локальное время зрителя их переводит браузер (toLocaleString()).
Объяснение блокировок в UI: Поле или действие, недоступное для правки (disabled), обязано объяснять пользователю причину конкретно (например: "сверено с банком — снимите отметку", "период закрыт", "системная запись, недоступна для правки"), а не просто быть серым без пояснения. Пример паттерна — lockReason() в resources/js/Pages/Finance/Transactions/Index.vue.
Право администратора на удаление без ограничений: Любой status/workflow-guard на удаление бизнес-записи (например "запись уже конвертирована в заказ-наряд", "заказ уже завершён" и т.п. — обычная проверка вида if ($model->status === 'X') { return ...withErrors(...) } перед delete()) обязан пропускать пользователя с ролью admin (User::isAdmin()) — паттерн: добавляй && !auth()->user()->isAdmin() к условию блокировки, аналогично и в bulk-удалении. В UI кнопка удаления не дизейблится для админа (только для остальных ролей, с поясняющим title — см. правило выше), а confirm()/диалог на фронте для админа обязан явно предупреждать о причине и последствиях обхода (например: "Запись уже оформлена в заказ-наряд. Удалить всё равно?"), а не просто молча удалять. Причина завести это правило: до внедрения связи Appointment↔WorkOrder (Фаза 9.4) заказы могли удаляться без отвязки записи, из-за чего в системе остались "зависшие" записи в статусе converted без реального заказа — и даже администратор не мог их удалить веб-интерфейсом, пришлось чинить точечно. Исключение — НЕ применяй этот обход к защитам целостности данных, которые не являются просто статус-меткой: сверка (is_reconciled), закрытие периода (finance_period_closures), системные справочники (Lookup.is_system), и любые операции, уже необратимо повлиявшие на склад/финансы (списанные остатки, проведённые транзакции) — там нужен явный откат через StockService/FinanceService, а не снятие блокировки.
Inertia.js & Vue: Для форм используй useForm из @inertiajs/vue3. При обновлении списков (поиск, фильтры) используй router.get(..., { preserveState: true, preserveScroll: true }).

НЕ разбрасывай переходы между такими страницами отдельными кнопками в DataTableToolbar #actions — так интерфейс выглядит по-разному в разных разделах. Кнопка в тулбаре уместна только для перехода в ДРУГОЙ раздел (например из HR → Взаиморасчёты кнопка "Настройки зарплаты" ведёт в Settings, у которого уже своя вкладочная навигация).
Tri-State Record Pattern (Паттерн 3 состояний) — единая терминология для этих трёх UI-состояний, используй именно эти названия в коде, комментариях и общении, не изобретай синонимы (например, "шапка" вместо "Форма" — баг наименования, а не альтернативный термин):
    * Панель просмотра: Выезжающая справа панель (<Offcanvas>) при клике на строку таблицы.
    * Карточка: Отдельная трёхколоночная страница (/crm/clients/{id}) с KPI-дашбордом и таймлайном.
    * Форма: Модальное окно по центру (<Modal>) — как для добавления новой записи, так и для редактирования существующей.
Иконки действий в списке (эталон, ОБЯЗАТЕЛЕН для любой Index-таблицы, где у записи есть все три состояния Tri-State Record Pattern или хотя бы Панель просмотра + Карточка): клик по всей строке <tr> (class="... cursor-pointer group") открывает Панель просмотра — не переход на отдельную страницу и не открытие Формы напрямую. В последней колонке строки — колонка "Действия" с иконками-кнопками в цветных круглых плашках (паттерн `w-8 h-8 rounded-full`, см. п.7 про цветные плашки вообще), каждая с `@click.stop`, чтобы не триггерить клик по строке: `ri-folder-open-line` (bg-info/10 text-info) — переход на Карточку (<Link>); `ri-pencil-line` (bg-primary/10 text-primary) — открыть Форму редактирования (только если у сущности вообще есть отдельная Форма-редактор шапки записи, не у всех есть); `ri-delete-bin-line` (bg-danger/10 text-danger) — удаление/отмена записи, с confirm(). Панель просмотра в подвале обязана дублировать переход на Карточку кнопкой "Открыть {сущность} →" (Link, на всю ширину, bg-primary text-white) и, если применимо, кнопку "Форма". Эталонная реализация — Operations/WorkOrders/Index.vue (WorkOrderController::index()), вторая подтверждающая — Warehouse/GoodsReceipts/Index.vue. Правило действует и для уже существующих списков — переводи их на этот паттерн по ходу любой правки затрагиваемой страницы, не обязательно отдельной задачей.
    * Иконка "удалить" НЕ обязана быть буквальным DELETE FROM — она обязана вызывать то действие, которое у ЭТОЙ сущности реально безопасно "убирает" запись из активного оборота. Для записей без SoftDeletes/hard-delete эндпоинта, которые уже повлияли на склад/финансы (см. п.8 — не удаляй такие записи впрямую), иконка вызывает существующий откат/отмену сервиса (например у GoodsReceipt — cancel(), который реверсирует остатки через StockService и переводит статус в 'canceled', сама запись и её позиции остаются для истории) — НЕ заводи отдельный деструктивный destroy() ради одной лишь красоты списка. Условие показа иконки — то же самое условие, при котором это действие вообще доступно у записи (например только status === 'posted').
Бейдж Локация/Юрлицо/Направление на карточках: Любая запись с branch_id (WorkOrder, Client, Employee, Transaction и т.п.) обязана показывать локацию — и, если у записи есть собственное legal_entity_id (пока только WorkOrder, см. п.4), юрлицо — и в Карточке, и в Панели просмотра (Offcanvas/preview), а не только в списке. Видимость зеркалит философию топбара (AppHeader.vue): бейдж локации показываем, только если у тенанта больше одной локации (page.props.branches.length > 1), бейдж юрлица — только если больше одного юрлица (page.props.legal_entities.length > 1) — на одноточечном/одноюрлицом тенанте бейдж лишний шум, а не полезная информация. Готовый компонент — resources/js/Components/PointBadge.vue (принимает :branch и :legal-entity, сам решает видимость по page.props) — используй его, а не дублируй условие в каждой карточке. У записей без собственного legal_entity_id (Client/Employee/Transaction) юрлицо НЕ показывай через branch->legalEntities() "если оно одно" — это способ РЕЗОЛВИТЬ юрлицо для документа (см. DocumentPlaceholderService::resolveLegalEntity()), а не факт принадлежности самой записи; если такой записи нужен явный выбор юрлица — заводи под неё собственное nullable legal_entity_id по образцу WorkOrder, а не выводи бейдж по слепку локации. Направление (BusinessDirection) НЕ дублируй на карточках заказа/клиента/сотрудника — это концепция уровня позиции (Service.business_direction_id), не самой записи целиком (заказ может содержать позиции из разных направлений сразу, WorkOrderItem не хранит business_direction_id вообще), у неё уже есть корректное отображение на уровне каталога (Settings/Services, Settings/ServiceCategories) — попытка агрегировать её на карточку заказа даёт хрупкий и вводящий в заблуждение код. ИСКЛЮЧЕНИЕ — Сделка (Фаза 17): у неё направление НЕ агрегируется по позициям, а задано явно и ровно одно — через воронку (`pipeline.business_direction_id`), поэтому на Карточке сделки и на карточке канбана показывать его МОЖНО и нужно. Правило запрещает выводить направление там, где его приходится ВЫВОДИТЬ ИЗ НАБОРА позиций, а не там, где оно хранится явно. Branch/LegalEntity — SoftDeletes; на записи, ссылающиеся на удалённую локацию/юрлицо (исторические заказы после удаления локации), eager-load для карточек делай через ->with(['branch' => fn ($q) => $q->withTrashed(), ...]) — иначе Eloquent применяет SoftDeletingScope даже к простому belongsTo() и бейдж молча покажет пустое значение вместо пометки "локация удалена" (PointBadge сам показывает суффикс "(удалена)"/"(удалено)" по branch.deleted_at/legalEntity.deleted_at, если они переданы через withTrashed).
История и Комментарии на Карточке: Каждая «Карточка» обязана иметь вкладку «История» — системная лента событий (создание, смена статуса, оплата, привязка связанной записи и т.п.), пишется ВРУЧНУЮ через App\Services\ActivityLogger::log() в конкретных локациях контроллеров человеческим текстом на русском. НЕ используй автологирование диффов полей (пакетный LogsActivity trait) — оно даёт нечитаемый технический шум вида «branch_id изменён с 3 на 5» вместо осмысленного «Заказ создан из записи в календаре». Комментарии и заметки менеджеров — ОБЯЗАТЕЛЬНО отдельная вкладка «Комментарии», никогда не смешивай с «Историей»: если несколько менеджеров параллельно комментируют, общая лента превращается в кашу, где не видно ни системных событий, ни обсуждения. Технически оба используют одну и ту же таблицу activity_log (пакет spatie/laravel-activitylog, миграция в database/migrations/tenant/ — это данные тенанта, не landlord), просто разные выборки на бэкенде по полю event (event='comment' — в «Комментарии», всё остальное — в «Историю») и один и тот же фронтенд-компонент <ActivityTimeline> (resources/js/Components/ActivityTimeline.vue), с полем ввода комментария только во вкладке «Комментарии» (проп comment-url). Модель подключает связь через трейт HasActivityLog (app/Models/Concerns/), а не через LogsActivity пакета. Ссылки на связанные записи внутри события — через properties.links (массив {type,id,label}), не парсинг ссылок из текста. Эталонная реализация — WorkOrderController + WorkOrders/Show.vue.
Много вкладок в одном блоке Карточки (эталон — HR/Employees/Show.vue): если у сущности несколько параллельных лент/списков (Выплаты, Начисления, История, Комментарии), они живут в ОДНОМ блоке средней колонки с переключателем вкладок, а не отдельными блоками друг под другом — иначе длинный список выдавливает Историю и Комментарии далеко вниз. Каждый список внутри такого блока пагинируется СЕРВЕРНО и НЕЗАВИСИМО (свой параметр страницы — `accruals_page`/`payouts_page`, и свой размер страницы `*_per_page` с ограничением min(max($v,5),100)); нельзя грузить их целиком «потому что вкладка всё равно скрыта». Компонент `<Pagination>` принимает опциональные пропсы `preserve-scroll`/`preserve-state` (по умолчанию false — обратная совместимость) — для пагинации внутри вкладки они ОБЯЗАТЕЛЬНЫ, иначе переход по страницам сбрасывает активную вкладку и прокрутку.
Массовая выплата ЗП (PayrollController::bulkPayout()): выплата нескольких начислений одной операцией — валидирует, что ВСЕ выбранные записи принадлежат одному получателю (employee_id/client_id) и находятся в статусе pending/accrual, затем в ОДНОЙ транзакции прогоняет их через приватный `payOne()` — тот же код, что и одиночная `payout()`, вынесенный ради переиспользования. Не дублируй логику создания транзакции: любая новая форма выплаты обязана идти через `payOne()`, иначе расчёт с кассой разъедется.
Roll-up Истории на карточках Клиента/Автомобиля: Их лента дополнительно подтягивает события WorkOrder/Appointment, у которых properties.client_id/vehicle_id указывает на эту запись — ActivityLogger::log() САМ копирует client_id/vehicle_id из $subject (если такие атрибуты у него есть), передавать их вручную на каждом вызове не нужно; запрос — ActivityLogger::feedFor($subject, $rollupField).
Точность текста события ОБЯЗАТЕЛЬНА: Событие может показываться не только в «Истории» своей записи, но и через roll-up в ленте другой (Заказ → лента Клиента/Автомобиля) — там неявный контекст страницы («мы сейчас внутри Заказа №12») теряется. Поэтому текст описания сам по себе обязан однозначно называть конкретную запись, к которой относится (номер заказа, дата и т.п.) — «Статус заказа №12 изменён на «Готов»», а не безличное «Статус изменён на «Готов»». Плюс — properties.links со ссылкой на эту запись, чтобы из чужой ленты можно было перейти к первоисточнику в один клик.
Компоненты: Обязательно использование <DataTable> (сама таблица — см. правило ниже), <DataTableToolbar> (поиск), <Pagination>, <BulkActions> (массовые операции) и <PageHelper> (сворачиваемые подсказки).
Единый компонент таблицы (<DataTable>, resources/js/Components/DataTable.vue): ЛЮБАЯ таблица списка записей (Index-страница CRM/Warehouse/Finance/HR/Settings/Central-admin и т.п.) ОБЯЗАНА использовать этот компонент вместо ручной вёрстки `<table>/<thead>/<tbody>` — он сам даёт zebra-полоски, hover, чекбокс-колонку (`selectable` + `v-model` на массив выбранных id, select-all включён автоматически), колонку действий (`has-actions`, слот `#actions="{ row }"`), клик по всей строке (`row-clickable` + `@row-click="row => ..."`) и пустое состояние (`empty-message="..."` для простого текста ИЛИ слот `#empty` для HTML/условной логики — например два разных сообщения "список пуст" vs "фильтр ничего не нашёл"). Пропс `columns` — массив `{key, label, align?, headerClass?, cellClass?}`; для страниц с пользовательскими колонками (ColumnSettingsModal/listView) передавай уже вычисленный `activeColumns` напрямую, для страниц со спец-выравниванием — оборачивай его в свой `computed`, добавляющий `align`/`cellClass` по `col.key`. Ячейка без своего слота рендерится как обычный текст `row[key]` — слот `#cell-<key>="{ row, value }"` нужен только для бейджей/иконок/составных двухстрочных ячеек/инлайн-виджетов (интерактивная кнопка внутри ячейки — обычное дело, просто не забывай `@click.stop`, если на странице есть ещё и `row-clickable`, чекбокс/actions-ячейки сами это `.stop` уже делают). Для catch-all кастомных полей (CRM/Clients, HR/Employees) — динамическое имя слота через `v-for`: `<template v-for="def in customFieldDefs" :key="def.key" #[`cell-${def.key}`]="{ row }">`. Для строк с принципиально другой структурой на некоторых строках (например colspan-схлопывающаяся строка ошибки, как в Central/Admin/Tenants) — слот `#row="{ row, columns }"` полностью переопределяет рендер `<td>` для ВСЕХ строк таблицы (условие "обычная строка / особая строка" пишет сам родитель внутри слота). Вложенные исходные данные (например модели внутри марок) сначала разворачивай в плоский список через `computed`/`flatMap` — компонент принимает только плоский `rows`. Это правило действует и для уже существующих таблиц — переводи их на `<DataTable>` по ходу любой правки затрагиваемой страницы, не обязательно отдельной задачей.
🚫 `<DataTable>` НЕ подходит для: (а) таблиц с drag-n-drop сортировкой строк мышью через `<draggable tag="tbody">` (vuedraggable) — компонент сам жёстко рендерит `<tbody>`, подменить его нечем; живые примеры, оставленные на голой вёрстке сознательно — Settings/Posts/Index.vue и блок «Статусы заказ-нарядов» в Settings/Dictionaries/Index.vue; (б) матриц прав доступа роль×объект с динамическими колонками-по-ролям и ячейками, читающими/пишущими вложенное состояние по двум ключам (`matrix[roleId][row.key]`, а не `row[col.key]`) — живой пример: Settings/RolesPermissions/Index.vue (все 3 таблицы). Расширение `<DataTable>` под drag-n-drop или под динамические колонки-матрицы — не делай самостоятельно попутно с несвязанной задачей, это отдельное архитектурное решение по явному запросу.
Сортировка по клику на заголовок, в т.ч. многоколоночная с приоритетом (`<DataTable>` + `useServerSort`): колонка с `sortable: true` в объекте `columns` становится кликабельной (стрелка ▲/▼/нейтральная ⇅ в заголовке). Обычный клик — заменяет сортировку целиком этой одной колонкой (цикл asc→desc→asc, обычное поведение для большинства случаев). **Shift+клик** — добавляет колонку к уже применённым со следующим приоритетом, не трогая остальные (цикл asc→desc→убрать из сортировки при третьем Shift+клике на той же колонке); когда сортировок больше одной, у иконки — маленькая надстрочная цифра приоритета (¹, ², ³...). Если UI-ключ колонки не совпадает с реальной колонкой БД (например `status` в разметке — это `is_active` в таблице), добавь `sortKey: 'is_active'` — именно это значение уйдёт в `sort_by`, а не `key`. Состояние — пропс `sort` (МАССИВ `[{key, dir}, ...]` в порядке приоритета, первый элемент главный), НЕ строка — компонент сам не хранит сортировку, эмитит `@sort` с уже посчитанным новым массивом. Composable `resources/js/Composables/useServerSort.js` — стандартный мост к серверной пагинации: `const { sort, onSort } = useServerSort('route.name', () => props.filters, () => ({ search: search.value, filters: filtersForm }))`, прокинь `:sort="sort" @sort="onSort"` в `<DataTable>`. ⚠️ Второй аргумент — ОБЯЗАТЕЛЬНО функция-геттер (`() => props.filters`), не сам `props.filters` напрямую: Inertia на каждый `router.get` подменяет `props.filters` на совершенно новый объект (не мутирует старый), поэтому переменная, захватившая ссылку один раз, реактивность после первого клика теряет — это был живой баг здесь (клик по заголовку срабатывал только один раз, повторный клик не переключал asc/desc), пока не завели через геттер. На бэкенде `QueryFilterService::apply()` принимает `allowedSorts: [...]` — обязательный белый список реальных колонок БД (без него `sort_by` просто игнорируется, а не "разрешено всё" — сырой sort_by никогда не должен идти в `orderBy()` без проверки, это чужой ввод); `sort_by`/`sort_dir` сами по себе всегда МАССИВЫ на уровне HTTP-параметров (даже для одной колонки — так их шлёт `useServerSort`, но и одиночный скаляр из ручного ввода в адресной строке тоже принимается), `apply()` проходит по ним циклом и делает `orderBy()` в том же порядке — порядок вызовов `orderBy()` и есть приоритет в SQL. Колонки, производные от связей/подзапросов (группа/роль/локация через relation, сегмент через HAVING и т.п.), JSON/translatable-поля (spatie/laravel-translatable — `name` у Product/ProductCategory/Position/ServiceCategory/TransactionCategory/Service) и посчитанные после пагинации PHP-агрегаты (например суммы начислений в HR/Payroll, себестоимость на складе) — НЕ включай в `allowedSorts` и не помечай `sortable`, простой `orderBy` их не потянет или отсортирует только текущую страницу. Для страниц БЕЗ серверной пагинации (небольшие, не растущие списки — библиотека шаблонов, справочники, каналы связи и т.п.) — `resources/js/Composables/useClientSort.js`, тот же интерфейс `{sort, onSort}` плюс `sortedRows`: `const { sort, onSort, sortedRows } = useClientSort(() => props.items)`, привяжи `:rows="sortedRows"` (не исходный проп) и `:sort="sort" @sort="onSort"` — принимает массив, `Ref`/`computed` или функцию-геттер, сравнивает только верхнеуровневые ключи объекта строки (для вложенных полей вроде `row.make.name` добавь на бэкенде/в `computed` плоский дубль-ключ, см. `modelRows` в `Settings/Dictionaries/Index.vue`). Раскатано на все таблицы на `<DataTable>` по всей системе (кроме заведомо составных/агрегатных, где сортировать нечем — см. `Settings/Payroll/Index.vue`, взаиморасчёты по подрядчикам используют `useClientSort`, по сотрудникам — `useServerSort`, т.к. первая таблица не пагинирована, а вторая пагинирована); новую страницу на `<DataTable>` заводи сразу с сортировкой по той же схеме.
Полосатые таблицы (zebra) — для случаев вне <DataTable> (см. исключения выше): Каждая строка <tr> в <tbody> любой таблицы (кроме заведомо однострочных/коротких списков без нужды в ней) обязана иметь odd:bg-gray-100/80 dark:odd:bg-gray-800/40 в дополнение к hover:bg-gray-50/50 dark:hover:bg-gray-800/30 — так строки визуально не сливаются. Это работает через CSS :nth-child(odd), поэтому корректно даже в перетаскиваемых (vuedraggable) таблицах — JS ничего вручную не считает. Внутри <DataTable> это уже встроено, отдельно заботиться не нужно.
Свёрнутые боковые панели (<CollapsiblePanel>): Наведение мышью на свёрнутую панель показывает её содержимое всплывающим поверх страницы (не меняя раскладку/ширину колонки), уход курсора — прячет обратно. Клик по стрелке — отдельное действие, разворачивает панель насовсем (сохраняется в localStorage). Кнопка-стрелка обязана быть выше всплывающей панели по z-index, иначе панель перекрывает и делает недоступным сам переключатель.
Dark Mode: Вся верстка обязана поддерживать темную тему через префикс dark: (например, bg-white dark:bg-[#313a46]).
Выпадающие списки с поиском: Для любого select, где список вариантов реально длинный и растёт со временем (клиенты, автомобили, сотрудники, локации, услуги/товары, посты, справочники и т.п.) — ОБЯЗАТЕЛЬНО используй <SearchableSelect> (resources/js/Components/SearchableSelect.vue) вместо голого <select>. Короткие фиксированные списки (2-6 вариантов — статусы, типы, да/нет) можно оставлять обычным <select>, поиск там не нужен. Это правило действует и для уже существующих select — переводи их на SearchableSelect по ходу любой правки затрагиваемой страницы, не обязательно отдельной задачей.
Мультивыбор — какой компонент брать: <EmployeeMultiSelect> (только сотрудники, без поиска — для коротких списков вроде администраторов заказа); <SearchableMultiSelect> (произвольные {id,label} + поиск, опционально creatable+lookupType для добавления значения справочника на лету — так выбираются роли клиента и цели ставок ЗП); <AssigneeMultiSelect> (исполнители позиции заказа — двухрежимный, Наёмные/Подрядчики, с блокировкой смешивания). Все три телепортируют панель в ближайший <dialog>-предок, если открыты внутри <Modal> — иначе панель уходит под модалку (см. правило про top layer выше).
Телефон клиента обязателен по умолчанию: без него невозможно понять, есть ли уже такой клиент в базе, — это главный признак дубля. Поле обязательно и в основной форме клиента, и во всех местах быстрого добавления («+» из заказа/записи/авто). Снять требование можно тумблером «Без номера», но тогда форма ОБЯЗАНА показать предупреждение о риске задвоить клиента. Серверная часть смотрит на флаг phone_required (ClientController::store()/update()) — не убирай его, иначе валидация станет чисто клиентской. При редактировании клиента, у которого телефона и так не было, требование не форсируется — иначе сохранение без единой правки упёрлось бы в валидацию значения, которое система раньше приняла.
Пополняемые списки (Creatable): Любой select/SearchableSelect, выбирающий значение из каталога/справочника (клиент, автомобиль, товар, услуга, группа клиентов и т.п. — сущность, а не фиксированный enum статуса/типа), обязан давать возможность добавить новый вариант, не покидая текущую форму. Для простых строковых Lookup-справочников (источник клиента, роль клиента, тип кузова и т.п.) — готовый <CreatableSelect> (resources/js/Components/CreatableSelect.vue, ввод текста + "Добавить «...»" прямо в выпадающем списке, POST на settings.lookups.store).
⚠️ ЖИВОЙ БАГ, НАЙДЕН И ИСПРАВЛЕН (2027, при работе над Фазой 17): `LookupController::store()`/`update()` годами сохраняли ТОЛЬКО `value`, `label` никогда не устанавливался — любая запись справочника, добавленная через `<CreatableSelect>` (единственный UI-путь создания таких записей, отдельного поля "label" в форме нет и не было) получала пустой `label` и потом отображалась пустой строкой везде, где UI показывает `.label`, а не `.value` (найдено на разбивке сделок по источникам, Фаза 17 этап 4 — донор-справочник `client_source`, но баг общий для всего механизма quick-add). Исправлено: `store()` теперь всегда пишет `'label' => $validated['value']` (форма не различает эти два поля — value и есть отображаемый текст); `update()` — ТОЛЬКО backfill (`$lookup->label ?: $validated['value']`), не безусловная перезапись — у записей, заведённых сидером/миграцией (`work_order_status`: `'new'` → `'Новый'` и т.п.), value и label специально РАЗВЕДЕНЫ (машинный слаг и человеческий текст), и эти записи тоже проходят через `update()` при правке цвета/статуса — слепая синхронизация стёрла бы их настоящий label. Существующие сломанные записи (пустой label во всех трёх тенантах на момент фикса) забэкфилены миграцией `2027_02_16_000000_backfill_empty_lookup_labels` (тем же условием: только там, где label пуст). Для полноценных сущностей со своими обязательными полями (Client, Vehicle, Product — и любых будущих) этот компонент не подходит (в Lookup нет места для телефона/марки/цены) — паттерн вместо этого: маленькая кнопка "+" рядом с <SearchableSelect> (иконка ri-add-line, тот же паттерн, что и у кнопки "Добавить группу" при выборе грейда клиента), открывающая компактную модалку ТОЛЬКО с обязательными полями сущности (для Client — локация/имя/телефон, остальное — потом в карточке клиента; для Vehicle — марка/модель/госномер), сабмит — обычный Inertia useForm().post() на УЖЕ существующий store()-роут сущности (crm.clients.store, crm.vehicles.store, WorkOrderController::storeProductQuick и т.п.) — НЕ заводи отдельный "quick"-эндпоинт, если у сущности и так минимум обязательных полей. После успеха форма страницы (Inertia redirect back) сама подтягивает обновлённый список; новая запись находится диффом списка до/после отправки (id, которого не было в старом списке) и подставляется в форму автоматически — гадать, какая именно запись только что создана, не нужно, т.к. id из ответа сервера однозначно её определяет. Для связанных сущностей (Client↔Vehicle) кнопка "+" работает СИММЕТРИЧНО в обе стороны: из формы заказа/записи можно сперва завести клиента и потом добавить его авто (поле "Автомобиль" → "+"), а можно и наоборот — открыть добавление авто без выбранного клиента и завести владельца прямо оттуда (кнопка "+" рядом с полем "Клиент" ВНУТРИ модалки быстрого добавления авто) — обе модалки при этом открыты одновременно (третий вложенный <dialog>), после сохранения клиента его id подставляется и в форму авто. Эталонная реализация — Operations/Appointments/Index.vue и Operations/WorkOrders/Index.vue. Правило действует и для уже существующих форм — добавляй кнопку "+" по ходу любой правки затрагиваемой страницы, а не отдельной задачей на весь проект сразу.
🚫 Модалку быстрого добавления (и вообще ЛЮБУЮ модалку, которая может открыться поверх другой модалки) НИКОГДА не верстай голым `<div class="fixed inset-0 z-[...]">` — оборачивай в общий <Modal> (resources/js/Components/Modal.vue). Причина не в величине z-index: <Modal> рендерит нативный HTML `<dialog>` через `.showModal()`, а такой элемент браузер кладёт в специальный top layer, который физически выше ЛЮБОГО обычного элемента страницы независимо от z-index — обогнать его никаким числом нельзя. Только ВТОРОЙ `<dialog>` (тоже открытый через `<Modal>`) корректно ляжет поверх первого — top layer стекуется по порядку открытия. Живой баг из-за нарушения этого: кнопка "+" (быстрое добавление клиента) внутри формы заказ-наряда (та открыта через `<Modal>`) открывала модалку клиента ПОД формой заказа, потому что модалка клиента была голым div с z-[200] — цифра выше, чем у формы заказа, но `<dialog>` всё равно выше любого div. Если родительская форма — не `<Modal>`, а такой же голый div (как в Appointments/Vehicles) — голый div с большим z-index технически сработает, но не полагайся на это: правило "всегда `<Modal>`" одно для всех случаев и не требует помнить, чем именно открыт родитель.
🚫 Любой useForm().post()/router.post(), отправляемый ИЗНУТРИ формы, которая сама открыта через <Modal> (быстрое добавление клиента/авто/товара и т.п. поверх другой открытой модалки), ОБЯЗАН передавать `preserveState: true` (вместе с `preserveScroll: true`). Без него Inertia после `redirect()->back()` полностью пересоздаёт компонент страницы, даже если это та же самая страница — а вместе с ним уничтожается (не через штатный `.close()`, а грубым удалением из DOM) родительский нативный `<dialog>`, который в этот момент ещё открыт. Живой баг из-за нарушения этого: после сохранения клиента в модалке "+" форма заказа оставалась на экране, но переставала реагировать на клики — вся страница молча получала новый (уже пустой) экземпляр компонента, а не просто обновлённые пропсы. `preserveState: true` заставляет Inertia переиспользовать текущий экземпляр компонента и просто обновить его пропсы (включая обновлённый список clients/vehicles) — родительская модалка остаётся живой и открытой.
🚫 Любой компонент с выпадающей плавающей панелью на `position: fixed` + `<Teleport to="body">` (нужен, чтобы панель не обрезалась overflow-контейнерами — так устроены <SearchableSelect>, <EmployeeMultiSelect>, <StatusBadgeSelect>) ломается, если используется ВНУТРИ формы, открытой через <Modal>: панель телепортируется рядом с `<dialog>`, а не ВНУТРЬ его top layer, и `<dialog>` (всегда выше любого обычного элемента вне зависимости от z-index — см. правило про модалки выше) визуально и по кликам перекрывает эту панель — список как будто открывается, но клики по пунктам никуда не попадают. Живой баг из-за этого: в форме создания заказа (открыта через <Modal>) SearchableSelect для клиента/авто переставал реагировать на клики. Фикс — телепортировать не всегда в document.body, а в ближайший `<dialog>`-предок, если он есть: `teleportTarget = containerRef.value?.closest('dialog') || document.body`, вычислять ПЕРЕД открытием панели (внутри toggle()), `<Teleport :to="teleportTarget">` вместо жёсткого `to="body"`. Тогда панель и диалог оказываются в одном top layer, и обычный z-index (250 у панели против 200 у диалога) снова работает как ожидается. Этот же приём обязателен для ЛЮБОГО нового подобного плавающего Teleport-компонента (датапикеры, кастомные выпадающие списки и т.п.), который может открыться внутри <Modal>.
8. "ПОДВОДНЫЕ КАМНИ" (СТРОГИЕ ЗАПРЕТЫ)
🚫 Никогда не трогай файлы в vendor/.

9. ПРАВИЛО ВЫВОДА КОДА (ACM - Absolute Character Match)

Суть правила: НИ ОДНА строка существующего кода не должна пропасть или переформатироваться как побочный эффект правки. Всё, что ты не менял осознанно, обязано остаться побайтово прежним.

⚠️ Как это соотносится с §1 (Edit — точечный diff). Формулировка «выводи весь файл целиком» относится к УСТАРЕВШЕМУ способу работы, когда патч выдавался человеку текстом в чат. При работе через инструменты Edit/Write она НЕ означает «переписывай файл целиком вместо точечной правки» — наоборот:
    * Edit (точечная замена фрагмента) — ПРЕДПОЧТИТЕЛЬНЫЙ способ изменить существующий файл. Он по построению не может задеть нетронутые строки, то есть выполняет требование ACM лучше, чем полная перезапись. Правка большого файла десятком Edit'ов — это правильно, а не лениво.
    * Write по существующему файлу — только когда файл реально переписывается целиком и осознанно. Перед таким Write убедись, что новое содержимое не короче оригинала без явной причины (удаление кода должно быть осознанным, не побочным эффектом усечения).
    * Запрещены в любом случае: сокращения, плейсхолдеры вида «// остальной код без изменений» (см. также §8), удаление пустых строк и переформатирование нетронутого кода.

Причина, по которой правило заведено: один из прошлых экспериментов с локальным AI-агентом в этом проекте закончился заменой всего routes/tenant.php на 4 строки вместо добавления одного маршрута — именно этот сценарий правило и запрещает.

📅 Фаза 9: Календарь и Запись (Appointments & Scheduling) — реализовано

📄 Фаза 12: Документооборот (Document Management) — реализовано
Генерация печатных форм (Акты, Счета, Договоры) из шаблонов с плейсхолдерами, для любой сущности (ядро: work_order/transaction/client, расширяется добавлением записи в реестр — см. ниже).
    * 12.1. Конструктор шаблонов — Settings/DocumentTemplates (App\Http\Controllers\Tenant\DocumentTemplateController::ENTITY_TYPES — реестр сущностей, аналог MessageTemplateController::TRIGGERS). Плейсхолдеры — {{ключ}} + ОДНА неглубокая табличная секция {{#items}}...{{/items}}, рендерится App\Services\Documents\DocumentRenderer — НЕ Blade::render() (тело шаблона редактирует тенант-админ, Blade дал бы выполнение PHP через @php — критично на мультитенантной платформе). Источник данных — App\Services\Documents\DocumentPlaceholderService::buildFor() (реквизиты юрлица — LegalEntity.requisites JSON + Account.is_default_for_invoicing, локация — Branch).
    * 12.2. Генерация — App\Services\Documents\DocumentGenerationService::generate(), синхронно (не через Horizon — единичный документ не bulk-операция из CLAUDE.md п.6). Номер — App\Services\Documents\DocumentNumerator, атомарный (DB::transaction + lockForUpdate на document_numerators), НЕ COUNT(*)+1 — пропуски номеров при удалении документа в общем случае штатны (как в Bitrix24/1С). Нумерация — отдельно на каждую связку (юрлицо, шаблон), year=0 сентинел вместо null, если у шаблона number_reset_yearly=false (NULL в unique-индексе MySQL не считается дублем сам с собой — год=0 гарантирует один нумератор на связку). Удаление — DocumentController::destroy() (Document — SoftDeletes), по явному запросу владельца платформы номер при этом переиспользуется: DocumentNumerator::reclaimIfLast() откатывает last_number на 1 назад, ТОЛЬКО если удаляемый документ — самый свежий выданный номер своей связки (сравнение по отформатированной строке, не по id) — типичный кейс "сформировал по ошибке, сразу удалил" не оставляет дыру. Документ, удалённый не по порядку (уже есть более новые), номер не возвращает — дыра в этом случае неизбежна и корректна, иначе разъехались бы номера документов, выданных после него.
    * 12.3. PDF — barryvdh/laravel-dompdf (чистый PHP, без Node/Chromium; default_font переключён в config/dompdf.php на 'DejaVu Sans' — дефолтный 'serif' не содержит кириллицы вообще). Файл хранится через spatie/laravel-medialibrary (Document::class implements HasMedia, коллекция 'file') на диске 'local' (НЕ 'public' пакета по умолчанию — документы содержат финансовые/персональные данные, публичной ссылкой по предсказуемому пути раздавать нельзя, скачивание только через DocumentController::download() с BranchScope). Раздел «Документы» (documents.index) — реестр со списком/фильтрами (тип шаблона/сущности/юрлица/период) — сайдбар-модуль 'documents' уже сидировался (ModuleSeeder), был скрыт до этой фазы тем же механизмом, что открыл «Общение» в Фазе 11. Генерация доступна и оттуда, и с карточек записи (вкладка «Документы» — WorkOrders/Show.vue, CRM/Clients/Show.vue).
    * 12.4. Конструктор шаблонов — визуальный редактор (Tiptap, @tiptap/vue-3) с переключением в HTML-код, плюс загрузка готового .docx: DocumentTemplate.format='docx' → App\Services\Documents\DocxToHtmlConverter конвертирует файл в HTML ОДИН РАЗ при сохранении (PhpWord IOFactory::load() + HTML Writer, чистый PHP, БЕЗ LibreOffice) — дальше это обычный html-шаблон, DocumentGenerationService не знает и не ветвится по происхождению. Табличная секция для .docx-шаблонов размечается НЕ маркерами {{#items}}/{{/items}} (в Word их некуда вписать ровно на границе строки таблицы) — DocumentRenderer сам находит <tr>, содержащий первый плейсхолдер секции (например {{item.name}}), и клонирует именно эту строку; тот же фолбэк молча работает и для html-шаблонов, если явных маркеров нет.
    * 12.5. Кириллица в PDF — НЕ полагайся только на config/dompdf.php default_font='DejaVu Sans': это фолбэк, применяемый лишь когда font-family вообще не задан в HTML. Если тело шаблона (написанное вручную ИЛИ полученное из .docx — Word всегда проставляет свой font-family типа Calibri/Times New Roman в экспортированном HTML) указывает любой другой font-family, dompdf резолвит его через vendor/dompdf/dompdf/lib/fonts/installed-fonts.dist.json в один из Base-14 PDF-шрифтов (Arial/sans-serif → Helvetica) — а у них нет кириллических глифов вообще, без единой ошибки на любом этапе, просто "?" вместо букв на готовой странице. Поэтому DocumentRenderer::render() принудительно вставляет `<style>*{font-family:"DejaVu Sans",sans-serif !important}</style>` в начало итогового HTML перед рендером в PDF — не убирай это без замены на другой механизм гарантированной кириллицы. Там же — safety-net: неподставленный `{{ключ}}` (типичный случай — {{legal_entity.kpp}} у ИП, там просто нет такого ключа в requisites, в отличие от ООО) вырезается регэкспом после рендера, чтобы сырой плейсхолдер физически не мог попасть в документ, уходящий клиенту.
    * 12.6. Документ — зафиксированный во времени артефакт, НЕ живая проекция связанной записи: сгенерированный PDF никогда не перерисовывается сам по себе при изменении заказа/клиента задним числом (иначе то, что уже реально отправили клиенту, могло бы молча "переписаться"). Вместо этого — Document::isStale() (аксессор is_stale, требует заранее eager-loaded documentable + branch.legalEntity — НЕ через $appends глобально, точечно через ->append('is_stale') в DocumentController::index()/WorkOrderController::show()/ClientController::show(), иначе N+1) сравнивает created_at документа с updated_at связанной записи и юрлиц локации-источника — если новее, в UI рядом с номером документа предупреждающая иконка. Пользователю — выбор из двух действий: DocumentController::regenerateAsNew() формирует НОВЫЙ документ (новый номер через тот же DocumentNumerator) с текущими данными, старый не удаляет, а помечает superseded_by_document_id (FK nullOnDelete — если новый документ потом удалят, старый сам вернётся в обычное "устарел") — в UI такой старый документ показывается серой неактивной пометкой "заменён", а не активным предупреждением; DocumentController::replace() — то же самое содержимое, но БЕЗ нового номера (DocumentGenerationService::replace() не обращается к DocumentNumerator), тот же id/номер, только created_at и файл обновляются — для случая "просто исправить уже выпущенный документ", когда отдельная запись в истории не нужна.
    * 12.7. Подписанты для блока подписи в печатных формах ("Поставщик ___ подпись ___") — CountryConfigService::signatorySchema() (должность/ФИО руководителя и бухгалтера), НЕ часть requisite_schema (та — налоговые номера, разные по странам) и не зависит от юрисдикции, поэтому один список, подмешивается в getForCountry()['signatory_schema'] и рендерится тем же паттерном "динамическая схема → requisites JSON", что и requisite_schema — сразу в ДВУХ формах: Settings/LegalEntities/Index.vue (юрлицо тенанта) и CRM/Clients/Index.vue (B2B-клиент — сам сторона сделки в договоре, вкладка «Реквизиты» при type=b2b). DocumentPlaceholderService уже разворачивает ВСЕ ключи requisites как {{legal_entity.*}}/{{client.*}} — новый код для рендера не понадобился, только добавление ключей в форму + DocumentTemplateController::COMMON_PLACEHOLDERS/CLIENT_ORGANIZATION_PLACEHOLDERS для подсказки в конструкторе шаблонов.
    * 12.8. Условные блоки шаблона `{{#if key}}...{{/if}}` (DocumentRenderer::renderConditionals()) — показывают кусок HTML, только если значение `key` в контексте непустое (та же truthy-конвенция, что уже неявно действует у опциональных плейсхолдеров вида `{{work_order.vat_rate}}`, приходящих пустой строкой, если недоступны). Нужны, чтобы ОДИН шаблон одинаково верно печатался в нескольких взаимоисключающих состояниях одной записи (эталонный кейс — НДС: юрлицо не плательщик / НДС включён в цену / начисляется сверх) — без этого примитива опциональное значение просто подставлялось бы пустой строкой, оставляя в документе "голую" статику вокруг него (например `<p>НДС : </p>`). Та же граница объёма, что и у `{{#section}}` (см. докблок класса) — один уровень, БЕЗ вложенности и БЕЗ отрицания/операторов сравнения: взаимоисключающие состояния выражаются не через `{{^if}}`/`unless`, а через отдельные заранее посчитанные на бэкенде флаги (`work_order.vat_inclusive`/`vat_exclusive`, `goods_receipt.vat_inclusive`/`vat_exclusive`, `item.has_vat` — DocumentPlaceholderService), автор шаблона просто оборачивает нужный кусок в нужный флаг. Резолюция — ДВА прохода тем же принципом, что и renderFlat(): сначала внутри каждой строки `{{#items}}` с контекстом ЭТОЙ строки (условия на данных строки, например `item.has_vat` — у накладной НДС считается по каждой позиции отдельно), затем по всему телу с общим контекстом (условия вне таблицы + условия внутри строк, ссылающиеся на общий контекст записи, например `{{#if work_order.vat_exclusive}}` внутри `{{#items}}`) — ключ, не найденный ни в одном из двух контекстов (опечатка, чужой тип сущности), safety-net'ом в stripUnresolvedPlaceholders() трактуется как ложь и блок вырезается целиком вместе с содержимым: клиенту в готовом документе НИКОГДА не должен светиться сырой `{{#if...}}`. Реестр условий для конструктора шаблонов — DocumentTemplateController::ENTITY_CONDITIONS (флаги записи целиком) и `conditions` внутри ENTITY_TABLE_PLACEHOLDERS (флаги по позиции) — отдельно от ENTITY_PLACEHOLDERS, т.к. это переключатели видимости, а не значения для печати; в UI (Settings/DocumentTemplates/Index.vue) под них отдельная подсекция "Условия", клик по которой ОБОРАЧИВАЕТ выделенный текст в `{{#if key}}...{{/if}}` (insertCondition()), а не просто вставляет тег в курсор, как обычные плейсхолдеры.

Применяется ТОЛЬКО к WorkOrder.discount_amount (не к позициям) в WorkOrderController::recalculateTotals() — автоматически, ПОКА WorkOrder.discount_is_manual=false; ручное задание через updateDiscount() ставит флаг в true и с этого момента авто-пересчёт скидку больше не трогает, вернуть — тот же updateDiscount() с параметром auto=true (UI — кнопка 'Сбросить и считать автоматически' в модалке скидки, WorkOrders/Show.vue).

🎯 Фаза 17: Воронка продаж, Сделки и Канбан-доска (Sales Pipeline) — В РАБОТЕ (этапы 1–4 готовы, этап 5 — по потребности)
План согласован владельцем. Закрывает участок «до согласия клиента»: сегодня система видит только то, что происходит ПОСЛЕ (запись в календаре и заказ-наряд), а переговоры, замеры, КП и повторные касания не фиксируются нигде. Раздел сайдбара — отдельный, «Продажи» (решение владельца: у воронки своя аудитория — менеджер, не мастер, и свои права доступа; вкладкой внутри «Заказы и Записи» её было бы неудобно закрывать от тех, кому она не нужна).

КЛЮЧЕВОЕ АРХИТЕКТУРНОЕ РЕШЕНИЕ (зафиксировано, не пересматривать без нового запроса владельца):
Сделка (Deal) — ОТДЕЛЬНАЯ сущность, а не статус клиента и не ранний заказ-наряд. Это продолжение уже принятого в Фазе 9 принципа «Запись (намерение) ≠ Заказ-наряд (факт)», на шаг раньше: Сделка — это переговоры о намерении.
    * Почему не флаг у клиента: у одного клиента может идти НЕСКОЛЬКО сделок одновременно (оклейка одного авто + полировка другого). Существующий булев `Client.is_lead` этого не выражает в принципе. Он ОСТАЁТСЯ как есть и продолжает работать — автоматической конвертации лидов в сделки НЕ делаем, вместо этого на доске предусмотрена подсказка «лиды без сделки».
    * Почему не статус заказ-наряда: заказ по построению уже «случился» — у него позиции, списание склада при завершении, оплаты, расчёт ЗП. Сделка на стадии «Думает» не должна существовать в этом контуре, иначе непроданные переговоры попадут в отчёты по выручке и загрузке постов.
    * Сделка НЕ ТРОГАЕТ склад и финансы — ровно по той же причине, что и Appointment: правки/отмены сделки не должны требовать отката складских или финансовых операций, потому что до конвертации их попросту нет. `DealItem` (опционально) — только предварительная смета для КП, полная копия смысла `AppointmentItem`.
    * Цепочка целиком: Лид (Client.is_lead) → Сделка (Deal) → Запись (Appointment) → Заказ-наряд (WorkOrder) → Оплата (Transaction). НИ ОДИН шаг не становится обязательным: заказ по-прежнему заводится напрямую, как и сегодня — минуя и сделку, и запись.

    * `pipelines` — воронки: name, `business_direction_id` (nullable — привязка к направлению деятельности), is_default, is_active, sort_order.     * Финансы: сделка сама переходит в стадию type=won, когда по связанному заказу прошла оплата — один вызов в `WorkOrderController::processPayment()`, там уже дёргаются кэшбек и автогрейд клиента (Фаза 14).

    * Документы: `entity_type = 'deal'` в реестре шаблонов + метод в DocumentPlaceholderService → КП печатной формой ДО создания заказа.
    * Кастомные поля: добавить 'deal' в entity_type (ОБА места — валидация CustomFieldController И объект entityTypes во фронте, см. §5) — плейсхолдеры в шаблонах заработают автоматически через CustomFieldPlaceholderService.

    * ЗП менеджеру за сделки — ОТЛОЖЕНО до этапа 5 (решение владельца): это единственный пункт, который требует новой ЦЕЛИ у PayrollRule (сейчас их ровно три: position_id|employee_id|client_id, см. §4 RULE_TARGET_COLUMNS), а расчёт ЗП — самое чувствительное место системы. Не трогай PayrollRule в рамках этапов 1–4.

ПРИЁМЫ ЛИДЕРОВ РЫНКА, ВЗЯТЫЕ В РАБОТУ (HubSpot/Pipedrive):
    * Протухание сделок (deal rotting) — карточка визуально помечается, если лежит в стадии дольше `stage.rotting_days`. Считается НА ЛЕТУ из `deal.stage_entered_at`, фонового джоба не заводить.
    * Обязательный следующий шаг — сделка без открытой задачи помечается как брошенная. Главная причина потери сделок не отказ клиента, а то, что о нём забыли. Требует этапа 2.
    * Взвешенный прогноз — итог колонки показывает и сумму, и сумму × probability стадии.
    * Обязательная причина проигрыша при переводе в стадию type=lost — обычный Lookup + CreatableSelect, новых механизмов не нужно.
    * Сохранённые виды доски — через СУЩЕСТВУЮЩУЮ модель `ListView` (entity_type='deal', поля filters/sort/is_shared/is_default уже есть и сейчас недоиспользованы), не заводи свою таблицу.
    * Быстрые действия с карточки (позвонить/написать/поставить задачу) без открытия сделки.

ПОДВОДНЫЕ КАМНИ ЭТОЙ ФАЗЫ:
    * 🚫 Канбан НЕ грузит все сделки разом: каждая колонка отдаёт первые ~20 карточек и подгружает остальные по кнопке, итоги по колонке считаются АГРЕГАТОМ в SQL, а не суммированием загруженных карточек. Это единственный способ, совместимый с запретом `->get()` для списков (§6).
    * 🚫 `<DataTable>` для канбана НЕ применим (drag-n-drop строк — см. §7), нужен отдельный компонент `DealKanban.vue` на vuedraggable. Это ожидаемое, а не нарушающее правило исключение.
    * Стадию с непустым содержимым удалять нельзя (тот же запрет, что у `work_order_status` в LookupController::destroy()), стадии type=won/lost неудаляемы в принципе — на них завязаны отчёты и автопереход при оплате.
    * Клиент у сделки ОБЯЗАТЕЛЕН (решение владельца): анонимных сделок «только с телефоном» не делаем — иначе телефон, главный признак дубля в системе (§7), окажется в двух разных местах и поиск дублей перестанет работать. Лид заводится сразу как Client с is_lead=true через уже существующую форму быстрого добавления.
    * Направление деятельности у сделки выражается ЧЕРЕЗ ВОРОНКУ (`pipeline.business_direction_id`), а не колонкой на самой сделке. Это НЕ противоречит правилу §7 «Направление не дублируй на карточках заказа/клиента» — там запрет на агрегирование направления по позициям заказа, которых у заказа может быть много и из разных направлений; у сделки же направление — реальное свойство её воронки, ровно одно и заданное явно.
