# Settings/RolesPermissions/Index.vue — ИСКЛЮЧЕНА ИЗ РЕФАКТОРИНГА DataTable.vue

Изучено: 2026-08-14. Решение: НЕ мигрировать на `DataTable.vue` — другой класс задачи.

## Почему не подходит под текущий DataTable.vue

Все 3 таблицы страницы («Доступ к разделам», «Доступ к полям», «Доступ к данным (Scopes)») — это не списки записей с колонками фиксированного смысла, а **матрицы прав доступа** (роль × объект), принципиально другой формы:

- Колонки — НЕ статичный набор полей записи, а **одна колонка на каждую роль тенанта** (`v-for="role in roles"` в `<thead>`), то есть их число и подписи целиком динамические и зависят от данных, а не от типа сущности.
- Ячейка — НЕ значение поля строки, а **интерактивный toggle/checkbox, читающий и пишущий во вложенный реактивный объект по двум ключам одновременно** (`moduleMatrix[role.id][module.required_permission]`, `fieldMatrix[activeEntityTab][field.key][role.id].can_view/can_edit`, `scopeMatrix[activeScopeTab][item.id][role.id]`) — это не `row[col.key]`, а `matrix[dynamicColumnKey][row.key]`.
- Нет ни чекбокс-колонки, ни колонки «Действия», ни пагинации, ни тулбара — вся машинерия `DataTable.vue` (`selectable`, `has-actions`, select-all) для этого сценария просто не нужна; полезной осталась бы только рендер-оболочка `<table>`/`<thead>`/`<tbody>` + `#cell-<key>`-слоты, но даже они потребовали бы протаскивать динамическое имя слота на каждую роль (`#[`cell-role_${role.id}`]`) — технически возможно (тот же приём, что уже использован для кастомных полей CRM/Clients, HR/Employees), но это принципиально ДРУГОЙ паттерн использования компонента, ещё не проверенный в этом рефакторинге ни разу.

## Итог
Оставить как есть. Это не «сложная таблица» уровня `Operations/WorkOrders` (тот всё ещё список записей, просто с инлайн-виджетами в ячейках) — это матрица прав, которая для честного переиспользования потребовала бы либо (а) специального режима `DataTable.vue` под динамические колонки-роли, либо (б) отдельного небольшого компонента `PermissionMatrix.vue`. Ни то ни другое не диктуется текущим объёмом рефакторинга — решение по этому классу страниц стоит принимать отдельно, по явному запросу, а не мимоходом внутри текущего пакета.
