# Финансы: контрагенты, системные статьи, депозиты — зафиксированные решения

Статус: **Фаза A реализована** (контрагент + системные статьи + основание «заказ-наряд»).
Дата фиксации решений: 2026-08-19. Реализация: 2026-08-19 (миграция `2027_02_22_000000_add_counterparty_and_system_categories`, тесты `tests/Agent/TransactionCounterpartyTest.php`).

## Контекст

Раздел «Финансы» принимает приход/расход/переводы, но все ручные операции обезличены
(нет контрагента, нет привязки к заказу). Кнопки оплаты внутри заказа/накладной/ЗП
хранят контрагента только текстом в `comment`. Статьи несистемные, личный счёт клиента
отвязан от транзакций.

## Подтверждённые решения владельца

### 1. Набор системных статей (утверждён)

`transaction_categories` получают `is_system` + `value` (slug), сидируются, защищены
от удаления/переименования (паттерн `Lookup.is_system`). Автоназначаются по потоку,
в ручной форме выбираются только нужного `type`.

| value | Название | type | Автоназначение |
|---|---|---|---|
| order_payment | Оплата заказа | income | оплата заказ-наряда |
| client_deposit | Пополнение личного счёта | income | депозит клиента |
| other_income | Прочий доход | income | ручной доход |
| purchase_payment | Оплата поставщику | expense | оплата накладной |
| payroll_payment | Выплата зарплаты | expense | ЗП штатному / подрядчику |
| refund | Возврат клиенту | expense | возврат |
| commission | Комиссия эквайринга | expense | авто, системная |
| other_expense | Прочий расход | expense | ручной расход |

### 2. Контрагент обязателен (утверждено)

Для ручных `income`/`expense` контрагент обязателен. Исключения (контрагент = null):
`transfer` и системная комиссия эквайринга.

## Уточнения по итогам анализа мировых СРМ (вопросы 1–2 владельца)

### Свободное поле для разовых контрагентов — НЕ используем

Отраслевой стандарт (1С, QuickBooks, Xero, NetSuite) — контрагент это запись справочника,
разовые заводятся «на лету». Свободное `counterparty_name` отменено. Итоговая модель:

- `counterparty_type` / `counterparty_id` — полиморфный morph на `Client` | `Employee` (nullable).
- Разовый контрагент = быстрый Client (роль «Поставщик»/«Прочий») через существующий
  `<CreatableSelect>`/кнопку «+» (паттерн §7 AGENTS.md).
- Свободным остаётся только `comment` (описание платежа), не идентичность.

### Депозит клиента — отдельный регистр от бонусов (валидировано)

Отраслевой стандарт (YCLIENTS, Altegio, DIKIDI, Mindbody, 1С «авансы покупателей»):
депозит (реальные деньги) и бонусы (лояльность) — два раздельных баланса. В проекте
это уже `Client.balance` (депозит/долг) и `Client.bonus_points` (лояльность). Задача —
связать `balance` с транзакциями (п.3.4), не смешивая с бонусной механикой.

## Модель депозита (уточнено владельцем 2026-08-19)

Депозит — ОДИН из источников оплаты, НЕ единый расчётный регистр. Три раздельных
регистра, не смешиваются:

| Регистр | Что это | Природа | Сгорает/возврат |
|---|---|---|---|
| Депозит (`Client.balance`) | собственные деньги клиента «на другие нужды» | обязательство (liability) | не сгорает, возвращаем |
| Бонусы (`bonus_points`) | начисляемая лояльность | бонусный регистр | по правилам программы |
| Долг по заказу | `WorkOrder.final_amount − оплачено` | дебиторка | по факту оплаты |

Оплата заказа — клиент ЯВНО выбирает источник (живые деньги / депозит / бонусы / микс).
Депозит НЕ списывается автоматически. Пополнение депозита = income (деньги пришли),
но НЕ выручка (рост liability). Списание с депозита в оплату заказа = БЕЗ движения по
кассе, просто `balance -= сумма` и долг заказа уменьшается.

## Не закрытые вопросы (для возврата к работе)

- Основание ручной операции — ТОЛЬКО заказ-наряд (WorkOrder). Привязка к приходной
  накладной (GoodsReceipt) и начислению ЗП (Payroll) в ручной форме — Фаза B: там
  кнопки оплаты уже существуют внутри карточек сущностей, а добавление их в общий
  список оснований несёт риск двойной выплаты (кнопка + ручная операция на ту же
  запись). Флагнуть владельцу при планировании Фазы B.
- Приоритет: Фаза A целиком vs A1–A5 по частям (см. анализ в обсуждении) — решено
  в пользу A целиком.

## Что реализовано в Фазе A (справочно)

- `transactions.counterparty_type`/`counterparty_id` — полиморф на `Client`/`Employee`
  (nullable). Заполняется автоматически из заказа/накладной/ЗП/процессинга, в ручной
  форме обязателен (кроме `transfer` и комиссии эквайринга), привязка проверяется
  по локации клиента/сотрудника.
- `transactions.work_order_id` — nullable FK; «Основание» в ручной форме (доход/расход),
  выбор заказа подставляет контрагента и статью «Оплата заказа» (бэкенд — фолбэком
  `systemId('order_payment')` при пустом поле), при сохранении создаётся
  `payable_type=WorkOrder`, долг заказа пересчитывается через `syncPaymentStatus()`.
- 8 системных статей (`value`-слаги, `is_system=true`) из таблицы выше; автоназначение
  в `WorkOrderController::processPayment` (order_payment), `StockService::receiveGoods`
  (purchase_payment), `PayrollController::payOne` (payroll_payment), комиссия эквайринга
  (commission). Системные защищены от правки/удаления (включая admin — целостность
  справочника, паттерн `Lookup.is_system`, §8 AGENTS.md).
- Бэкфилл старых операций — `App\Services\FinanceCounterpartyBackfill` (массовая
  команда `php artisan finance:backfill-counterparties`), идемпотентен, не трогает
  уже заполненные строки.
- UI: блоки «Основание (заказ-наряд)» и «Контрагент» в форме операции, колонки
  «Контрагент»/«Основание» и фильтры по ним, бейдж «Системная» и блокировка правки
  системных статей в справочнике.
